# ADR-087:特征漂移监控 —— 训练时存基线,一个作业算 PSI

日期:2026-08-30
状态:**已实现,未部署验证**

## 问题

`docs/project/roadmap.md` P4 的 C 线(完整 MLOps)只剩这一条:**特征漂移
监控**。[ADR-085](085-inference-payload-logging.md) 已经把它的前置补上了
(推理留痕落进 `iceberg.ml.inference_log`,2026-08-30 端到端验过)。

**为什么这件事值得做。** 模型上线之后不会报错 —— 它对任何输入都会给出
一个预测。真正的失效方式是**输入的数据慢慢变了**:用户结构变化、上游埋点
改了口径、某个特征的采集坏了变成恒定值,而模型还在按旧世界的规律给答案。

这类失效**没有任何现有告警会响**:HTTP 是 200,延迟正常(`platform-inference`
看板上 P95 依然 9.7ms),Pod 健康,黄金链路探针绿的 —— 探针发的是固定的
测试向量,它永远"通"。只有把线上分布和训练分布放在一起比,才看得见。

## 决定

### 1. 不引入新组件,写成一个 `jobs/` 作业

roadmap 里那句判断就是这个决定:"有了 `iceberg.ml.inference_log` 之后,
漂移就是「对同一个字段比较线上分布和训练集分布」,那是 `jobs/` 里写一个
作业的事,不是一个新组件"。

市面上的漂移监控产品(Evidently、WhyLabs、Arize)解决的是"我有几十个模型、
几百个特征、要看板和告警路由"。这个平台现在有**一个** demo 模型。引入一个
组件的代价(部署、升级、又一套认证、又一个要维护的 UI)远超它此刻的收益,
而 `jobs/` 这套机制(写 `job.yaml` + 一个 py,自动变成 CronWorkflow)
2026-08-30 刚实机验证过。

**什么时候该重新考虑**:模型数量到两位数、或者需要"漂移了自动触发重训"
这种编排的时候。那时候这个作业算出来的 `ml.feature_drift` 表本身就是
现成的数据源。

### 2. 基线在**训练时**写进 MLflow tag,不在分析时重建

这是这份 ADR 里最要紧的一条。

漂移问的是"线上进来的数据,和**当初训练它的**数据比,变了没有"。那个
"当初"只有训练的那一刻知道。等到几周后想做分析时再去重建训练集分布 ——
重建出来的是**那时**的数据,不是训练时的。**得到的结论会是错的,而且不会
有任何地方报错**:PSI 照样算得出来,数字看着也合理。

所以 `scripts/train_demo_model.py` 在 `fit()` 之后把每个特征的分位数边界
+ 均值方差写进 MLflow 的 `feature_baseline` tag。基线跟着模型版本走。

**为什么是 tag 不是 artifact**:平台镜像里是 `mlflow-skinny`,没有 boto3
—— 下载 artifact 会在**运行时**才炸,而那时候作业已经跑了一半。tag 走
REST,skinny 就够。20 个特征的边界约 1.5KB,远低于限制。

**没有基线的模型版本会被跳过并说明原因**,不猜、不用当前数据凑一个。

### 3. 用 PSI,而且存分位数边界不只存均值方差

PSI(Population Stability Index):按训练集的分位数把特征分成 10 个等频桶,
看线上样本落进各桶的比例偏离了多少。

    PSI = Σ (线上占比 - 训练占比) × ln(线上占比 / 训练占比)

**为什么不是均值方差**:只看均值方差的话,"分布形状变了但均值没变"这种
漂移完全看不出来 —— 一个特征从单峰变成双峰,均值可能纹丝不动。分桶比较
看得见形状。

**空桶按 1e-6 算而不是跳过**:跳过的话,"线上完全没有落进某个桶"这个最强
的漂移信号会被算成 0 贡献 —— 而它恰恰是最该报的。

**阈值 0.2 是经验值,不是理论值**,`job.yaml` 里明确写了这一点。真实模型
上线后应该按它自己的历史 PSI 分布重新校准。

### 4. 专用 Trino 账号,而且**只放行 `ml`、不放行 `audit`**

这个口子比 OPA 里已有的两个都危险,值得单独说:

| 账号 | 它能看到什么 |
|---|---|
| `openmetadata_service` | 只采元数据(表名/字段名),看不到任何一行 |
| `iceberg_maintenance_service` | `ALTER TABLE ... EXECUTE`,不返回数据行 |
| **`feature_drift_service`** | **真的把推理输入一行一行读出来** |

推理输入很可能包含个人数据。为什么仍然值得开:

- 漂移监控**在数据上就是做不到"不看数据"**,它要的就是分布本身。替代
  方案(在推理链路上实时算统计量、只落聚合值)是另一套架构,代价高得多,
  而且会把统计口径钉死在写入时 —— 想换一个分箱方式就得重放历史。
- 挡住它的后果不是"更安全",是**模型静默失效没人知道**。

三条收窄让"值得"成立:

1. **只放行 `ml`,不放行 `audit`** —— 它没有任何理由读查询审计。有一条
   专门的测试(`test_feature_drift_service_denied_on_audit`)盯着这个区别,
   防止以后有人图省事把它并进那两条规则。
2. **专用账号,不复用 `notebook_service`** —— 那个账号是所有 notebook 和
   作业共用的,给它开口子等于"任何能提交作业的人都能读全部推理输入"。
   这个错 2026-08-30 在 `iceberg_maintenance_service` 上犯过一次,被既有
   测试当场拦下。
3. **结果表 `ml.feature_drift` 建在同一个敏感 schema 里** —— 虽然是聚合
   值,仍然是从个人数据推出来的,不该因为"只是统计量"就漏出去。

## 还没做的

- **告警**:算出漂移只会打印和落表,不会通知任何人。按 zhenghe 明确要求,
  真实告警渠道等上生产再接([ADR-081](081-alert-delivery-verified-with-echo-sink.md)
  的机制那一半已经验过)。落表之后接一条 Prometheus 规则是后续的事。
- **只覆盖数值特征**。类别型特征的漂移要用别的度量(卡方 / JS 散度),
  demo 模型全是数值特征,没有为了完整性去写用不上的代码。
- **没有"漂移了自动重训"**。那是编排,不是监控,而且在没有真实业务模型
  之前讨论触发条件是空的。
- **label drift / concept drift 没做**:那需要真实标签回流,这个平台还
  没有那条链路。
