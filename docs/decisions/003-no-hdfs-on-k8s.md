# 003. 不在 k8s 里重建 HDFS/YARN,联邦查询现有遗留集群

- 状态: 已采纳(2026-08-08)

## 背景

现有生产环境已经有一套遗留 Hadoop 集群(HDFS/Hive/HBase/Doris,规模约 300 张表 / 100T,下游消费逻辑不复杂)。新平台的目标之一是未来能替换掉这套旧系统,但不能一次性推翻重来。

## 决策

新平台不在 Kubernetes 里重新搭建 HDFS/YARN。新数据落地到 MinIO + Iceberg(见 [ADR-002](002-iceberg-lakehouse.md))。对现有遗留集群里的数据,用 Trino 联邦查询直接接入,按需渐进式地把数据迁移进 Iceberg,而不是整体搬迁。

## 理由

- 容器化 HDFS(DataNode 强依赖本地磁盘、NameNode HA 复杂)在 k8s 上是反模式,运维成本高,本地 16GB/arm64 环境也跑不动。
- 如果既保留旧 HDFS、又在 k8s 里建一套新 HDFS、又上云原生存储,会变成同时维护三套系统,维护成本不可控。
- Trino 联邦查询是成熟的过渡路线:不用先做一次性 ETL 就能让新平台的用户查到旧数据,给渐进迁移留出时间窗口。

## 后果

- 需要在 Trino 里配置连接到遗留集群的 Hive connector(联邦查询遗留 Hive Metastore + HDFS)。
- 遗留集群本身的运维(扩容、故障处理)仍按原有方式进行,不属于本项目 Phase 0-3 的范围,在 Phase 4 才正式纳入迁移计划。
- 如果未来某个具体场景确实需要 HBase 或类似 KV 存储的能力,单独评估,不代表要在 k8s 里恢复整套 Hadoop 生态(见架构清单里 HBase/Doris 标记为 Backlog/可选)。

## 补充(2026-08-08):兼容的边界

联邦查询是"渐进迁移的手段",不是目标本身——目的是不做一次性大迁移,不是要长期维护一套兼容层。表不多(约 300 张)、下游消费逻辑不复杂,这意味着迁移窗口可以很短。原则是:**兼容成本低就做,不低就直接切,不为兼容而兼容**。如果 Trino 联邦查询这条路径实际做起来比预期复杂(比如遗留 Hive 的某些字段类型、分区策略和 Iceberg/Trino 对不上,需要专门写转换逻辑),优先评估"干脆一次性把这批表转成 Iceberg"是不是比"长期维护联邦查询的兼容包袱"更划算,不要默认选兼容这条路。
