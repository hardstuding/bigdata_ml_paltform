# 055. 对外部(Codex)项目评审的响应:采纳哪些、延后哪些、为什么

- 状态: 已采纳(部分立即执行,部分明确延后并说明原因)

## 背景

用户在 2026-08-15 请 Codex 对这个项目做了一轮独立评审,产出记在
`docs/claude-improvement-recommendations-2026-08-15.md`(分两次追加,
第一次是 P0/P1 工程问题清单,第二次追加了角色成熟度评估、5 条产品主线、
交接规范)。用户要求判断如何优化这份文档、并在后续工作中维护好相关
文档——这份 ADR 就是那个"判断"的记录:不是把评审内容原样照抄执行,是
说清楚采纳了什么、为什么这么分期、原文档本身怎么处理。

## 评审质量判断:不是走过场,已验证属实

抽查了两条可独立核实的具体指控,都是真的,不是泛泛而谈:

1. `scripts/21-bootstrap-cloud-vm.sh` 的数据盘选择逻辑,注释写"找容量
   最大的那块",代码实际是"遍历取第一个无挂载点/无文件系统的"——注释
   和代码不一致,已修复(枚举全部候选、唯一候选才自动选、2 个以上拒绝
   并要求显式指定 `DATA_DISK_DEVICE`、格式化前额外校验不是根盘),在
   真实云主机上重新跑过验证不影响已有状态。
2. 历史上真实发生过 `kubectl delete namespace airflow` 误删
   `namespace data` 的事故(翻原始会话 `.jsonl` 记录核实,不是评审凭空
   猜的)——这条连同"这个项目对破坏性操作缺少系统性防护"的判断都成立,
   已经补进 memory(`feedback_destructive_ops.md`,之前这个项目的
   memory 系统里完全没有这条记录,是又一次真实的记忆遗漏)。

`environments/cloud-full/STATUS.md` 里"远程加载脚本还没做"这条具体指控
也核实属实(`scripts/22-load-image-cache-remote.sh` 早就写好且用过,
文档没跟上,而且和同一份文档"进度清单"那节自相矛盾)——已经在 STATUS.md
里更正,并把"改完一处要检查另一处有没有跟上"这条写进了对应的更正说明。

## 决策:P0 立即做,P1 明确延后,原因不是不认可

### P0(评审原文四条:开机门禁、Trino 访问闭环、破坏性操作防护、cloud-full
基础设施固化)—— 采纳,按下面顺序处理

- **数据盘选择 bug**:已修复(见上)。
- **破坏性操作防护**:评审建议的是"统一集群操作 guard"(context 校验+
  namespace 白名单+目标解析预览),这次先做轻量版——删除类命令执行前
  显式打印目标清单等确认,不是完整的一套 guard 框架。原因:这个项目一贯
  的取舍是不为了"看起来完整"引入没有真实使用场景验证过的重框架(见
  ADR-030 对生成器/抽象层的态度),轻量版先用起来,真的碰到"delete 类
  操作反复出现同一种误用模式"时再考虑要不要收敛成统一框架。
- **按量资源开机门禁**:采纳,做一个 preflight 脚本(检查本地缓存完整性、
  云端可达性、当前是否有可立即执行的工作),但不做评审建议的"预计费用"
  这类需要外部计价 API 的功能——没有稳定的免费计价接口,做了也是猜的
  数字,不如不做。
- **Trino 权限真正执行(OPA 上线)**:评审的方案(差异报告、bootstrap
  grants、回滚路径、用户在场切换窗口)全部认可,但**这一条本来就已经
  决定要等用户在场时再做**(ADR-051 写得很明确),这次不是因为评审才
  延后,是评审确认了这个延后决定是对的,不是消极拖延。

### P1(环境 overlay 重构、三个自建工具补测试锁依赖、扩大 CI、统一部署
入口、镜像缓存 digest 校验)—— 明确延后,不是否定

这五条每一条单独展开都是数小时到跨天量级的工程投入,评审自己也建议
"先做 P0 再做 P1"。延后的具体原因:

- 现在正处于 cloud-full 部署过程中(云主机在计费),不适合在这个时间点
  启动一次跨越 ~30 个组件定义的环境 overlay 重构——这类重构做一半比
  不做风险更高(local-lite 和 cloud-full 都可能被搞坏),需要一段"专门
  收口基础设施"的时间,不适合夹在计费资源正在运行的过程中顺手做。
- 三个自建工具补测试/锁依赖/构建镜像这条,认可优先级,但同样需要专门
  时间,不适合现在切进去做——现在切换会打断 cloud-full 这条主线,评审
  自己也提醒"一次只维护一个当前主线"。

**这不是说 P1 不重要,是排期问题,写清楚是为了不让"延后"被误读成
"决定不做"。**

### 角色成熟度评估 + 5 条产品主线(A-E)—— 采纳评估结论,不现在展开实现

评审这部分是这次追加的内容,判断:这是真实、有价值的战略输入(纠正了
"组件部署完 = 角色能用"这个容易想当然的判断),但**内容属于路线图/
backlog 层面,不属于"这次会话该做的任务"**——五条产品线每条都是独立的
大型交付,不应该被塞进当前这轮 cloud-full 部署工作里一起做。处理方式:

- 评估结论(角色成熟度矩阵、5 条产品主线概要、路线优先级建议)已经
  摘要进 `docs/architecture.md` 的路线图部分,作为 Phase 4 之后的方向性
  参考,不是本 ADR 重复整理一遍——完整内容以
  `docs/claude-improvement-recommendations-2026-08-15.md` 原文为准。
- 不现在展开任何一条产品主线的具体实现,遵守评审自己给的"路线优先级
  建议":先做 P0 可靠底座,再谈产品主线。

### 交接规范(TASK-xxx 格式、结束工作前检查清单、"陌生维护者演练")——
采纳,已经在实践

用户明确提过"项目随时可能交接给新的 AI/人类"这条底线要求(见 memory
`project_core_requirements`),评审这部分是把这条要求具体化成可执行的
格式和检查清单,判断:直接有用,采纳。落地方式:

- 结束一段工作前的检查清单(当前分支/commit/是否 push、各环境计费资源
  状态、后台任务/SSH 隧道是否还开着、真实完成度分几层、失败未解决事项、
  是否有未回写 git 的手工变更)——已经是 `environments/cloud-full/
  STATUS.md` 和这份 ADR 在做的事,不重复建一份新文档,以后每次收尾都
  对照这个清单过一遍。
- TASK-xxx 单项任务交接格式——这个项目现在的任务粒度大多数时候是
  "一个 ADR 对应一块工作",已经隐含了目标/范围/状态/验证这几项,暂时
  不额外套一层 TASK-xxx 模板,避免同一件事被两套格式重复记录。如果以后
  出现"一个 ADR 装不下、需要拆多个可独立交接的子任务"的场景,再引入
  这个格式,不提前套用。

## 原文档(`claude-improvement-recommendations-2026-08-15.md`)怎么处理

改动位置,避免以后有人以为这份文档"没人看、没人处理"。
