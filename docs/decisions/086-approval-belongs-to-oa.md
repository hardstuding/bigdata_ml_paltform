# ADR-086:审批流程外包给 OA,平台只保留策略和执行

日期:2026-08-30
状态:**协议已改对(`APPROVAL_BACKEND=oa`),没有真实 OA 可对接,未验证**

## 起因

zhenghe 2026-08-30:「我感觉你当前设计的这套表权限申请,不一定能用。设计得
有点差。我之前好像和你说过,未来可能要接入到公司的 OA 系统的。」

**这个判断是对的**,而且比"能不能用"更具体 —— 问题不在有没有对接口
([ADR-045](045-approval-backend-notifications-escalation.md) 已经留了
`APPROVAL_BACKEND=webhook`),在**接口的形状是错的**。

## 错在哪

翻 `dispatch_step()` 就能看出来:webhook 模式下,平台每轮到一级就 POST 一次,
body 里带着 **`approver_username`** —— 也就是说:

> 平台自己算出"该谁批",然后请 OA 去让那个人批。

这是反的。**OA 才是有组织架构和审批规则的那一方**。具体后果:

| 现在的做法 | 接了 OA 之后会怎样 |
|---|---|
| `get_manager_chain()` 从 `employees.csv` 推直属上级 | 那份是 demo 数据。公司真实的汇报线在 OA/HR 里,平台这份要么过期要么冲突 |
| `build_approval_steps()` 算出几级、每级谁 | OA 有自己的审批链规则(会签/或签/代理人/请假转交),平台算的这套会被忽略 |
| 每一级单独 POST 一次,等一次回调 | 粒度错了。OA 眼里这是**一张单子**,不是 N 张 |
| 状态机在平台的 sqlite 里 | 真相在 OA,平台这份变成影子副本,两边必然分叉 |
| 平台做了申请页/审批页/催办/超时升级 | 用户在 OA 里点,这些页面大部分作废;催办和升级更是 OA 的强项 |

**一句话:我们把"审批系统"本身做出来了,而那恰恰是最该外包的部分。**

## 分界线:什么留在平台,什么给 OA

留在平台的,是**OA 不可能知道**的东西:

- **这张表是几级、需要什么强度的审批** —— 数据治理策略,来自表的安全等级
  标注(ADR-043/044)。OA 不知道 `iceberg.demo.orders` 比 `demo.users` 敏感。
- **表负责人是谁** —— 来自数据目录(ADR-043),不是汇报线。
- **执行**:批准结果 → `table-access-grants.csv` → OPA 生效(ADR-051)。
  **这是平台独有的,OA 做不了。**
- **到期回收**(ADR-050)、**权限交接**、**留痕**。
- **申请入口**:因为要从数据目录里选表,这一步在平台更顺手。

给 OA 的:

- **谁审批** —— 汇报线、代理人、请假转交、会签/或签
- **审批的 UI 和催办**
- **审批过程的留痕**(平台只记最终结果)

## 协议改成什么样

**一张申请单一次 POST,一个最终结果一次回调。** 不再按步拆。

平台 → OA(申请提交时,一次):

```json
{
  "request_id": 42,
  "applicant": "analyst001",
  "table_fqn": "iceberg.demo.orders",
  "security_level": 2,
  "reason": "季度对账要看订单明细",
  "required_approval": {
    "levels": 2,
    "policy": "L1:直属上级 + 表负责人;L2:上级的上级",
    "table_owner": "manager001"
  },
  "callback_url": "https://<平台>/table-access/request/42/oa-callback"
}
```

**注意 `required_approval` 里没有 `approver_username`** —— 平台说的是
"这张表需要两级、其中一级必须包含表负责人 manager001",**不是**"请让张三
批"。谁是直属上级由 OA 决定。

OA → 平台(审批结束,一次):

```json
{"token": "<共享密钥>", "status": "approved", "note": "...", "approvers": ["li", "wang"]}
```

平台收到之后:写 grants.csv → push → OPA 5 分钟内生效。

## 现在做了什么

`APPROVAL_BACKEND` 现在有三档:

- `local`(**默认**)—— 平台自己收批准点击。**测试阶段用这个**,不需要 OA。
- `webhook` —— ADR-045 那套按步 POST。**保留但标记为不推荐**,它的形状是
  错的,留着只是为了不破坏可能已经存在的对接。
- `oa` —— 上面这套整单协议。**这是接公司 OA 时该用的那档。**

zhenghe 2026-08-30:「测试阶段,不用太严谨。未来生产你留好配置项就可以。」
所以这次**只把协议和配置项做对**,不做真实对接 —— 没有对接目标,做了也
只能是自己想象的样子。

## 没做的(接 OA 那天要做)

- **身份对齐**:OA 里的人和 Keycloak 里的人怎么对上(工号?邮箱?)。
  这决定了回调里的 `approvers` 怎么落到审计记录里。
- **平台这边的审批页面要不要下线**。`oa` 模式下它是空的(所有单子都
  `pending_external`),但留着不碍事,而且 OA 挂了可以临时切回 `local`。
- **`employees.csv` 的去留**。`oa` 模式下审批链不用它了,但**权限交接和
  到期通知还在用**,不能直接删。


---

## 2026-08-30 补:从数据目录发起申请,怎么做而不用二开 OpenMetadata

使用方:「最好的方式是在 openmetadata 里能直接看当前这个用户的权限,并且
点击其中一个按钮,就会跳转到 OA,并把对应的信息等带过去。但是这样好像会
导致 openmetadata 被二开,未来升级麻烦。」

**这个顾虑是对的,而且代价比想象的大。** 我们刚在 2026-08-26 把 OpenMetadata
从 1.13.3 升到 2.0.0(大版本,逐条核对过 breaking changes)。一旦分叉,
以后每次升级都要重新合一遍改动 —— 而这个平台明确的原则是"能复用就不自建、
能不改上游就不改"。

### 方案:用 OpenMetadata 的扩展点,不碰它的代码

OpenMetadata 有一个**给我们用的**扩展位:**自定义属性(Custom Properties)**。
这个平台已经在用了 —— `registeredOwner` 和 `securityLevel` 就是建表注册
工具写进去的(见 `ensure_table_custom_properties()`)。它们会显示在表的
详情页上。

再加一个 **markdown 类型**的自定义属性(比如 `申请访问`),值是一个链接:

```
[申请访问这张表](https://<平台门户>/table-access/request?table=iceberg.demo.orders)
```

markdown 属性在 OM 的表详情页上**渲染成可点的链接**。效果就是你要的
"在 OpenMetadata 里点一个按钮跳走并带上信息",而**一行 OpenMetadata 的
代码都没改**,升级完全不受影响。

链接指向平台自己的申请入口,不是直接指向 OA —— 因为:

- OA 的地址、单据类型、字段名会变,而这个属性是写进**每一张表**的,
  改一次要重写全部表的实体。指向平台,平台再转给 OA,改的只有一处配置。
- 平台这一跳还要补上 OA 不知道的东西(安全等级、表负责人、策略要求几级)。

### 另一半:**不要让 OA 直接读 OpenMetadata**

zhenghe 提到「OA 上读取这份数据,就会有审批流」。这条要特别注意:

**如果 OA 直接调 OpenMetadata 的 API,那么每一次 OM 升级都可能打破 OA 的
集成。** 我们刚经历的 1.13.3 → 2.0.0 就改过实体结构;而 OA 那边通常不是
我们能随时改的系统,一旦它坏了,修复周期以周计。

正确的做法是平台提供**一层很薄、很稳定的接口**给 OA:

```
GET /api/table-governance?table=iceberg.demo.orders
→ {"table_fqn": "...", "security_level": 2, "table_owner": "manager001",
   "required_approval": {"levels": 2, "policy": "L1:直属上级 + 表负责人;L2:上级的上级"}}
```

这层接口的**唯一职责是隔离** —— OM 怎么变、字段叫什么、认证怎么做,都关在
平台这边;OA 只认这个契约。契约本身很小(表名进,治理属性出),小到几乎
不会需要改。

### 现在做了什么

- ✅ 那个只读的治理接口(`/api/table-governance`),给 OA 和别的系统用。
- ✅ 建表注册工具写一个 markdown 自定义属性,让表详情页上出现"申请访问"
  的可点链接。
- ✅ 顺带修一个隐患:自定义属性的 `propertyType` 之前是**写死的 UUID**,
  而我们刚跨过一个大版本 —— 改成按名字(`string`/`integer`/`markdown`)
  在运行时查,不再赌 UUID 跨版本不变。
- ❌ **明确不做**:OM 里显示"当前用户有哪些权限"。那需要读登录用户身份,
  是 OM 的前端职责,不二开做不了。

  **zhenghe 2026-08-30 拍板不做**,原话:「这个其实暂时没有那么重要,如果
  涉及二开,可以不做,免得以后升级麻烦。有些非必须的功能和版本升级的方便
  性,还是要做抉择。」

  **替代**:平台门户首页已经有「我的表权限」那一栏(2026-08-30 实机验证
  过),快到期的会标黄。要在两个地方看到同一份东西,门户这边成本低得多。

  这条取舍规则已经写进 `CLAUDE.md`,以后遇到同类需求照它判断,不用每次
  重新讨论。
