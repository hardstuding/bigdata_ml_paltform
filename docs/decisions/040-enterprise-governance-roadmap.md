## 用户原话:7 条企业级治理需求(2026-08-09)

> 我还想到未来的一些开发管理需要,这些是否有些是能通过现有的工具来做,
> 有些要自己实现呢?

1. **建表工具**(明确表负责人、安全等级等)
2. **权限管理**:通过 OA,用户可以快速发起权限的申请。
   - 安全等级 1 的数据表:经过(申请人)职级 +1、表负责人 审批
   - 安全等级 2 的数据表:经过 +1、+2、表负责人 审批(**是在等级 1
     基础上叠加 +2,不是只要 +2** ——2026-08-13 用户复述时说成"职级+2
     和表 owner",丢了"+1 也要过"这个累加关系,这里以原文为准)
   - 安全等级 3 的数据表:在等级 2 基础上,再加指定负责人审批
   - 通过 OA 后,用户(或角色)拿到对应权限(读、写、管理等)
3. **资源隔离**
4. **权限交接**
5. **资源回收**(权限用着用着没人用了,要能识别并回收——2026-08-13
   复述时完全没提到这条)
6. **深度回溯**(大数据常见场景,整条链路需要重新刷数据——2026-08-13
   复述时也没提到)
7. **任务依赖**

补充背景:用户当时生产环境实际用的是 **DolphinScheduler**,不是
Airflow——功能不缺,但和其他工具的生态兼容性差,这次重搭平台才改用
Airflow。DolphinScheduler 的告警能力("可以快速支持各类告警的配置")
被提出来当作参考对象,这也是 Alertmanager 多渠道通知设计(ADR-034)
的部分灵感来源。

## 当时的分析:哪些有现成工具、哪些要自己写

| 需求 | 判断 |
|---|---|
| 1. 建表工具(负责人/安全等级) | **半现成**。OpenMetadata 本身有 Owner 和 Tag/Classification 字段能存这些元数据,但"建表时强制填负责人和安全等级"这个流程约束没有现成工具会管,需要一个薄的自建入口把这些信息写进 OpenMetadata |
| 2. 权限管理 + OA 多级审批 | **基本要自己写**,是 7 条里最重的一块——没有现成工具做"按安全等级动态路由审批链、对接企业 OA、审批通过后自动在 Trino/Ranger 下发权限"这一整套 |
| 3. 资源隔离 | **现成工具能覆盖大半**:计算隔离靠 k8s 命名空间 + ResourceQuota,或 Trino 的 resource group;数据侧隔离靠 Ranger/Trino 的权限策略 |
| 4. 权限交接 | **要自己写**,是需求 2 那套权限系统的一个子功能 |
| 5. 资源回收 | **数据现成,流程要自己写**:Trino/Ranger 都有访问审计日志(能看出"这个权限多久没用过"),但"定期识别 + 发起回收流程"这个自动化要自己搭 |
| 6. 深度回溯 | **基本现成**:Airflow 本身支持 DAG 从某个点往后重跑(backfill/clear task instances),Iceberg 也有时间旅行/快照回滚;前提是 DAG 设计得干净(任务幂等、依赖关系清楚),更多是工程规范问题,不是缺工具 |
| 7. 任务依赖 | **完全现成**,Airflow 核心能力 |

**结论**:真正需要大量自建开发的其实只有**需求 2(权限 OA 审批系统)**,
3/4/5 都是挂在这套系统上的功能,6/7 靠已有工具 + 良好的设计习惯就能
覆盖。这是个不小的自建项目,当时的建议是等平台核心(存储/计算/编排/
目录)都稳定之后再单独立项做——**这个结论仍然成立,这份 ADR 只是补
记录,不重新讨论一遍"现成 vs 自建"**。

## 用户追问里的 3 条补充信息(同一次会话)

1. **自建前端/开发者门户,降低非工程角色的使用门槛**:用户原话——
   "是否需要把很多开发 demo 沉淀下来?最好通过自建前端,把一些开发
   规范约束下来,保留接口调用,这样对于前面说的数分、运营角色比较
   友好"。这是一个比"权限申请门户"更大的产品设想:把平台开发规范
   (建表规范、接口调用方式等)固化成 UI 引导、降低非工程背景角色使用
   门槛的门户。`apps/permission-request-app/` 目前只覆盖"申请加入某个
   group"这一个薄切片,离这个设想还有距离。
2. **权限 OA 要抽象成可插拔的**:用户原话——"有些需要和外部对接的,
   这种最好抽象成一些比较通用的,比如权限 OA 流程那个,能够快捷接入
   现成 OA,或者完全需要自己写"。设计权限 OA 审批系统时不能假设一定
   要自建全套,要预留"对接企业现有 OA 系统"的抽象接口——和这个项目
   "可插拔外部基础设施"(ADR-030)是同一个设计取向,只是这次是对接
   企业内部系统,不是外部开源组件。
3. **Superset 企业微信告警二次开发,是用户已有的代码资产**:用户原话
   ——"少部分工具可能要做二开,比如 superset,我之前自己还做了二开,
   让支持企业微信推送告警。这个未来我们可以拿我现有的项目,你后续再
   结合着改造"。这不是从零设计,是一个具体的、用户已经拥有的代码资产,
   属于"以后要接进来"的明确 TODO。2026-08-13 这次会话里已经做的
   Alertmanager 企业微信通知模板预留(ADR-034)算是这条 TODO 的一部分
   已经在推进,只是当时不知道背后有这段渊源——两者应该在真正实现企业
   微信通知时一并考虑,不是各做各的。

用户当时的原话是:"其他我没什么问题,你看看有没有需要讨论的,有些你
可以记下来作为 todo,有些你也可以接着往下,我们一步一步来。"——这是
一条明确的"记录下来"指令,过去那次会话没有执行到位,这就是 2026-08-13
"发现规划丢了"的根本原因。

## 后果

- 这 7 条需求 + 3 条补充信息里,除了"资源隔离"之外,都还没有具体设计
  或实现,只是这次把内容准确归档进仓库——不代表接下来立刻按顺序实现,
  按 ADR-004 的分级画像,这些大多是 cloud-full/prod 阶段的工作,
  local-lite 阶段的重点还是把核心链路跑稳。
- "资源隔离"相对独立、可以单独先做,不依赖上面其他条目,已经在
  `docs/architecture.md` 的"还没定的事"里单独记了一条,不和这份 ADR
  混在一起推进。
- **这次事故本身的教训**:凡是用户明确说"记下来"/"这个是 todo"的内容,
  必须当场写进仓库的持久化文档(ADR、architecture.md、专门的 backlog
  文件),不能只停留在对话文本里——见新增的
  `docs/operations/troubleshooting.md` 里"怀疑内容丢失时怎么排查"那条,
  以及为此新写的一条 feedback 类型记忆。

## 补充:2026-08-13/14,AI 角色化 + 知识沉淀(单独提出,不属于上面 08-09 那 7 条)

同一轮"担心规划丢了"的会话里,用户还额外提出一条新需求,严格说不属于
2026-08-09 那 7 条,是当次新提的第 8 条方向。用户原话:

> 还有ai要介入,相当于单独的角色
>
> 我还想到一个事,目前工作中会接入AI,这个平台上也会有很多人大量使用AI,
> 目前很多工具都可以接入AI,这时候就需要AI在协助人类的过程中,能把很多
> 知识整理沉淀。这个也是很关键的一环

拆成两层:
1. **AI Agent 应该是平台里独立的一类身份**(不是人类账号的影子)——
   这条和 `platform/iam/` 现有的人类身份体系(Keycloak groups/roles)
   是平行的新设计面,目前完全没有设计,`platform/iam/` 里没有任何 AI/
   service-identity 相关的角色定义。
2. **人类用平台各种工具时如果接入了 AI 助手,这些交互过程中沉淀的知识
   应该被整理、能被团队复用**——这条是 2026-08-14 晚和用户讨论"Superset
   等工具是否有对外 AI 助手会记录对话、能否整理沉淀"时具体化出来的同一个
   方向,调研过开源选型见该次对话(企业知识问答类产品,如 Onyx/原
   Danswer,更贴近这个需求;Mem0/Zep/Letta/Cognee 这类是给单个 agent
   用的记忆层 SDK,不是团队知识库,概念上是两类不同的工具)。

**这条这次同样只归档,不展开设计**,原因和 ADR-040 主体 7 条一致——
本身没有明确的实现优先级,且依赖"AI 在平台各工具里到底怎么接入"这个
更上游的问题还没有答案(目前 Superset 等工具里没有内嵌 AI 助手,是
外部通过 MCP 连接的模式)。**这次没有再犯"记下来但没落地"的错**:第一
版内容被写进了一个 Claude Code 临时 plan 文件(`~/.claude/plans/`,不在
git 仓库里),后来被同一会话下一轮计划复用覆盖掉了,只在
`docs/architecture.md`"还没定的事"里留下"AI 角色化/知识沉淀"两个词、
没有实质内容——这份 ADR 补充就是把这条从"两个关键词"恢复成有出处、
有原话的记录。

**How to apply:** 以后如果又讨论到"AI 助手/知识沉淀/团队记忆共享"这类
话题,不用再当成新想法从头调研,先看这一节确认是否和用户原始诉求(AI
独立身份 + 交互知识可复用)对得上,再决定是否需要正式立项。
