# 010. 组件可选、可对接企业已有服务,版本要锁定并记录测试过的升级路径

- 状态: 已采纳(2026-08-08)

## 背景

不是每个环境都要用我们自己部署的每个组件——有些企业已经有现成的服务(比如 Redis、Kafka),重复部署一套既浪费资源又可能和已有业务冲突(见接入共享集群前要做体检这条,[troubleshooting.md](../operations/troubleshooting.md) 和相关待办)。另外组件版本升级如果没有明确记录"测试过哪个版本能升级到哪个版本",容易出现"不敢升级"或者"升级了才发现兼容性问题"。

## 决策

1. 每个组件在 `environments/<profile>/` 的 values 里都要有一个显式的开关(部署自己的 / 对接企业已有服务 / 不启用),不能是"代码里硬编码肯定要装"。
2. 每个组件的 chart/镜像版本必须显式锁定(`targetRevision` 精确到版本号,不用 `latest`、不用范围通配符),已经是现在的做法,这条只是把它明文写成规则。
3. 升级前先在 `local-lite` 或专门的测试环境验证,验证过的升级路径记录到 [`docs/operations/upgrade.md`](../operations/upgrade.md),格式:`组件 X.Y → X.Z,验证日期,验证人,注意事项`。不是升级了就完事,要把"这个路径测过、安全"这个事实沉淀下来,而不是每次升级都重新摸索。

## 理由

- 用户明确要求:能对接企业已有服务的组件不要重复部署,而且要"标注好支持的版本",升级要经过测试,参考成熟项目的做法。
- 这和 [ADR-004](004-environment-profiles.md) 的 profile 机制是同一个思路的延伸:profile 决定"开不开",这条决定"开的话用谁的、版本多少、什么时候验证过要升级"。

## 后果

- `environments/` 目录从"只有 README 占位"变成需要真正承载这些开关和版本记录的地方,Phase 1 之后组件变多时要落地(现在 Phase 0-1 的组件还比较少,直接写在 Application 的 valuesObject 里,还没到非拆分不可的规模)。
- 对接企业已有服务(比如已有 Redis)时,我们自己的 Application 要能整个跳过部署、只留客户端配置指向外部地址——这要求组件的接入方式本身就是"配置驱动",不能假设"这个服务一定是我们自己起的"。
