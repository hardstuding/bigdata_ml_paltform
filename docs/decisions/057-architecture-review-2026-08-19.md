# 057. 架构评估与结构性调整:从"组件视角"转到"角色视角"

- 状态: 已采纳,分三批执行(第一批文档结构重组已完成,第二/三批是工程改造,已排进 BACKLOG)
- 日期: 2026-08-19

## 背景

zhenghe 2026-08-19 提出:"我感觉最近做的事有点多,但也开始有点乱了,
需要你整理一下当前的文档,核心是架构设计上看看要不要调整优化一下。
我怕这么堆叠开发下去,后续就无法维护了。……核心是从各个角色的角度出发,
做好这个产品。"

这不是一次"整理文档"的请求,是"堆叠开发"这个感受背后有没有真实的结构
问题。这份 ADR 是评估结论 + 决定改什么。评估只用可核实的事实(文件
数量、目录内容、本次会话真实发生过的故障),不用主观印象。

## 核心诊断:组织原则和实际目标不一致

**项目的组织原则仍然是"组件视角"(部署并验证了哪些开源组件),但实际
目标早在 2026-08-15 就转成了"角色视角"(某个岗位能不能完成一件真实
工作)。两套框架同时存在、互不换算,所以每来一件新事都是往某个列表
后面追加——这就是"堆叠"感的来源。**

证据:
- `docs/architecture.md` 的主路线图是 Phase 0-4 的组件里程碑表格,
  紧接着又有一节"Phase 4 之后:从'组件都部署了'到'每个角色真的能用'",
  提出 A-E 五条面向角色的产品主线,并注明"这五条现在都还没开始"。
  两个框架并列,没有换算关系:Phase 0-4 全绿,不代表任何一个角色能
  干完一件事。
- `docs/project/roadmap.md` 的优先级是 P0/P1/**P1.5/P1.6/P1.7**/P2。带小数的
  层级不是优先级,是"不同日期追加的批次"——说明这份清单一直在被追加,
  没有被重新排过序。
- 唯一面向角色的文档 `docs/usage-guide.md`(108 行)只覆盖分析师一个
  角色,而且自己承认 notebook 那一段是缺口。

### 这个不一致造成的最大后果:平台只对一个角色是完整的

按角色重新核对"今天真的能用什么"(依据:`apps/definitions/` 里 28 个
已部署的 Application vs `environments/cloud-full/pending-definitions/`
里 13 个没部署的),结果非常整齐——**没部署的那批,几乎精确地就是
除分析师之外其它角色所需要的东西**:

| 角色 | 关键依赖 | 状态 |
|---|---|---|
| 数据分析师 | Trino / Superset / dbt / 建表工具 / 权限申请 | **全部已部署** |
| 运维 | ArgoCD / Prometheus / Grafana / Loki / Alertmanager | **全部已部署** |
| 大数据开发 | Airflow(已部署)+ Spark Operator / SeaTunnel / Kafka | **调度器起来了,它要调度的引擎全部没部署** |
| 算法工程师 | JupyterHub → MLflow → KServe | **入口和中间环节没部署,只有最后一环 KServe 部署了** |
| 数据治理 / 管理 | OpenMetadata(血缘/资产)/ 管理驾驶舱 | **OpenMetadata 没部署;驾驶舱从没开始** |

这个结论比"还有 8 个组件没拉起来"有用得多:它说明缺口不是零散的,是
**按角色成块缺失**的。算法工程师今天连第一步都迈不出去,而唯一为他
部署好的是流程最末端的推理服务。

### 为什么这 8 个组件没起来:环境抽象只做了一半

`pending-definitions/` 这个机制是 2026-08-08 为 **6GB 内存的 colima
本机**设计的——当时四个组件一起部署把虚拟机打满、集群失联,所以把重
组件挪出 `apps/definitions/`,让 `apps-root` 不同步它们。

**但 cloud-full 是 16 vCPU / 64 GiB(见 `environments/cloud-full/STATUS.md`),
早就不受这个约束了。这 8 个组件今天没起来,不是资源不够,是"哪些组件
该启用"这件事至今仍然靠人工在两个目录之间 `git mv`,而这个机制本身
不区分环境。**

这正好补上了 2026-08-16 那次环境配置重构没覆盖的部分。一个完整的环境
抽象需要三层,目前只做了第一层:

1. **环境取值**(域名 / 端口 / 协议)——✅ 已完成,
   `environments/<env>/config.yaml` + `templates/` + `render-environment-config.py`
2. **组件选择**(这个环境启用哪些 Application)——❌ 仍是手工 `git mv`,
   **这是 8 个服务没起来的直接原因**
3. **规格分档**(副本数 / resources / 持久化)——❌ 仍是手工改 values

## 其它已确认的结构性债务

按"真实造成过多少损失"排序,不按理论严重性:

### 1. 没有镜像构建流程,用运行时 `pip install` 代替(损失最大)

全仓库只有 1 个 Dockerfile(`apps/feast/feature-server-image/`),CI 里
没有任何镜像构建。而 **8 个地方在容器启动时现装 Python 依赖**:
platform-portal / permission-request-app / table-registration-app /
iam-sync / superset / airflow dags(dbt)等。

这不是理论风险,**仅 2026-08-16 一个晚上就因此产生了四次真实故障**:
- Superset 反复被 SIGKILL(exit 137):pip 装到一半超出 startupProbe
  预算被杀,每次重启前功尽弃,看起来像"一直在自愈但永远好不了"。
- platform-portal 的修复"看起来没生效":新 pod 卡在无保护的 pip install
  超过 7 分钟不 Ready,Service 就一直把流量发给旧 pod,外部现象和
  "改错了"完全一样。
- 曾经尝试换阿里云 PyPI 镜像加速,结果 `pip-install.sh` 把包装到了
  Superset 进程读不到的路径,产生更严重的 `ModuleNotFoundError`,
  只能回退。
- 同一份 manifest 在不同时间部署会得到不同的运行时(没有 lock 文件),
  不可复现。

代价还包括:每次 pod 重启都要重新联网下载;离线/内网环境根本装不起来
(这对"能原样上生产"这条底线是硬伤)。

### 2. "生成式单一源码"脚本在增殖(现在 3 个)

`sync-app-configmaps.py`(src/app.py → ConfigMap)、
`sync-airflow-dags-configmap.py`(dags/*.py → ConfigMap)、
`render-environment-config.py`(templates/ → 部署文件)——三个脚本都在
实现同一个模式:"从源文件生成部署产物 + `--check` 防漂移"。

它们各自都是对的(而且都接进了 CI),但**这个模式一直增殖,本身就是
"缺一个构建步骤"的症状**:因为没有构建产物的概念,每多一类需要生成的
东西,就要多写一个专用脚本 + 多一个可能漂移的点。

### 3. 部署后需要人工补丁,而且会静默回退

`scripts/07-fix-trino-liveness-probe.sh` 必须在**每次** Trino 的 pod
template 变更后重新执行——任何产生新 ReplicaSet 的改动都会把
livenessProbe 还原成 chart 那个坏掉的默认值。本次会话里就重跑了 3 次。

这不是 GitOps,是"GitOps 加一个没人会记得的手工步骤"。

### 4. `docs/project/current-work.md` 退化成了只增不减的排障日记(591 行)

`CLAUDE.md` 要求接手者第二个读它,目的是知道"现在唯一的主线任务是什么、
下一步做什么"。但这个信息埋在**第 220 行**,前面是 219 行按日期堆叠的
排障叙事。这直接违反项目自己定的第一条底线("新的 AI/人类不依赖这次
对话记忆也能接手")。

排障记录本身有价值,不该删——但它是**日志**,不是**状态**,两者混在
一份文件里,状态就被日志淹没了。

### 5. `scripts/` 51 个文件,编号约定已经撑不住

00-26 是带编号的顺序步骤(但顺序现在其实由 `bootstrap-all.sh` 负责),
另外 24 个没有编号。里面混着四类完全不同的东西:部署步骤、演示脚本、
本机开发便利工具、云主机生命周期管理、以及像 `07-fix-*` 这样的临时
补丁。编号暗示的执行顺序和实际调用关系已经对不上了。

### 6. 3000 行自建 Flask 控制面,但没有当作产品来管

platform-portal(384 行)、table-registration-app(635 行)、
permission-request-app(1972 行)。**这部分不应该砍掉——权限模型和
统一门户恰恰是这个平台相对于"装一堆开源组件"的差异化所在**,ADR-032/
043/044/045 的分级审批链是真实的产品能力。

但它现在的交付方式是"源码塞进 ConfigMap + 启动时 pip install",不是
一个有构建、有版本、有回滚的产品。1972 行的审批引擎用这种方式交付,
是目前最需要优先改的一处。

## 决策

### 第一批(本次已执行):文档结构按角色重组

1. **新增 `docs/project/capability-matrix.md` 作为角色视角的唯一权威**:五个角色 × 每个
   角色的完整工作链路 × 每一环今天的真实状态(能用 / 部分 / 缺失),
   以及缺失的那环具体卡在哪个组件或哪条债务上。这份文件取代
   `architecture.md` 的 Phase 表格成为"我们做到哪了"的第一入口。
2. **`architecture.md` 的 Phase 0-4 表格降级为历史记录**,顶部指向
   `project/capability-matrix.md`。Phase 表回答的是"部署了什么",保留有价值,但它不再是
   衡量进度的标尺。
3. **`project/current-work.md` 拆成状态和日志两部分**:文件本身只保留"当前
   主线 / 下一步 / 在跑的后台任务 / 收尾检查清单",按日期堆叠的排障
   叙事移到 `docs/journal/`,按月归档。
4. **`project/roadmap.md` 重排**:取消 P1.5/P1.6/P1.7 这种批次伪装成的优先级,
   改成按"阻塞哪个角色的哪条能力"排序。
5. **新增 `docs/decisions/README.md`**:55 个 ADR 的主题索引。

### 第二批(下一段专门时间,已排进 BACKLOG 最前面):补上构建流程

**决定引入镜像构建,不再用运行时 `pip install`。** 范围按收益排序:
先做 3 个自建 Flask 应用(它们同时受"启动慢""不可复现""ConfigMap 塞
源码"三个问题影响,收益最大),再看 iam-sync,Superset 这类官方 chart
的 bootstrapScript 最后处理(它的替代方案是自定义镜像,改动面更大)。

配套:依赖锁定(requirements 带哈希或 lock 文件)、CI 构建并推到
registry、manifest 引用带 digest 的镜像。这一步做完,第 1、2、6 条债务
同时消解大半——`sync-app-configmaps.py` 这类脚本届时可以退役。

**明确不做的**:不引入 Kaniko/Tekton 这类集群内构建体系(对单人维护
的项目过重),用 GitHub Actions 构建 + 推 registry 就够。

### 第三批:补上环境抽象的第 2、3 层

让"这个环境启用哪些组件"和"用哪一档规格"变成
`environments/<env>/config.yaml` 里的声明,`pending-definitions/` 这个
靠目录位置表达启用状态的机制退役。做完这一步,cloud-full 上那 8 个
组件应该是"改一行配置 + 渲染"就能拉起,而不是人工 `git mv`。

顺序上第三批可以先于第二批做,因为它直接解锁 3 个角色的能力(见上面
角色表),而第二批解决的是可靠性和可维护性。**建议顺序:第三批 → 第
二批**,理由是先让每个角色有东西可用,再让交付方式变扎实。

## 后果

- 好的一面:"我们做到哪了"这个问题从此有唯一答案(`project/capability-matrix.md`),而且
  这个答案天然对齐用户真正关心的东西(某个岗位能不能干活),不会再
  出现"Phase 全绿但没人能用"这种表里不一。
- 代价:`project/capability-matrix.md` 需要跟着每次能力变化更新,又多了一份要维护的文档。
  缓解办法是它取代而不是叠加——Phase 表和 README"当前状态"那段都改成
  指向它,不再各自维护一份会过时的进度描述。
- 诚实记录:这份 ADR 只做了评估和文档重组,**第二、三批都还没有动工**,
  不要因为这里写了决策就以为已经实现。BACKLOG 里对应条目的状态才是准的。
