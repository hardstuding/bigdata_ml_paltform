# 007. 消息队列用 Redpanda,不默认上 Kafka

- 状态: 已采纳(2026-08-08)

## 背景

Phase 2 数据工程层需要消息队列能力(行为数据总线、后续 CDC/实时特征的输入)。经典选择是 Kafka,但 Kafka 本身(+ZooKeeper 或 KRaft)在资源受限环境下运维负担不小,而这个项目的目标是"要消息能力",不是"运营一个 Kafka 集群"。

## 决策

默认用 Redpanda。它是 Kafka 协议兼容的单二进制实现,资源占用明显更低,k8s 部署也更简单。

## 理由

- 协议兼容意味着上游(Spark/Flink/SeaTunnel 等)的 Kafka 客户端代码不用改,迁移到真 Kafka 的成本可控。
- 符合"组件独立可升级、不过度设计"的原则 —— 先用运维成本更低的方案跑通场景,真的遇到 Redpanda 满足不了的需求(比如需要 Kafka 生态里某个 Redpanda 还不支持的特性)再切换。

## 后果

- 如果生产环境本身已经有企业级 Kafka 集群(比如遗留系统里就在用),Phase 4 对接生产时需要重新评估:是复用现有 Kafka,还是继续用 Redpanda。这个决策届时更新。
