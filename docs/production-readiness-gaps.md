# 离"企业级生产可用好用"还差什么(2026-08-23 盘点)

zhenghe 2026-08-23:"有些设计可能是我没想到的,你可以给我建议一下,
我们的目的是企业级生产可用好用。"

这份文档是**主动提出的缺口清单**,不是对某个具体需求的答复。挑选标准
是两条:(1) 在真实企业环境里**不做会出事**,而不是"做了更完整";
(2) 现在**确实没有**——写之前逐条在仓库里查证过,已经做了的没有列进来
(比如 Postgres 多副本已经是 `{{RES:postgres_instances}}` 参数化的,
备份恢复 2026-08-13 真做过演练,这两条就不在下面)。

排序是我的建议顺序,依据是"不做的后果有多难挽回"。

---

## 1. 数据质量断言 —— ✅ 已做(2026-08-23,见 [ADR-065](decisions/065-data-quality-on-openmetadata.md))

复用了 OpenMetadata 自带的 Data Quality(zhenghe 提示的方向,核实后确认可行),
三条断言已在 cloud-full 实机跑通,并用一条故意失败的探针证明了绿灯能变红。
下面是当初判断它最危险的原因,保留下来是因为**这个判断依据本身仍然成立**,
后续给新表配断言时是同一套理由。

**当时的现状:**全仓库搜不到任何数据质量/断言相关的东西。有作业调度、有血缘、
有监控,但没有任何一层在回答"**跑出来的数据是不是对的**"。

**为什么这条排第一:**作业挂了会告警,有人管;**数据错了不会告警**,它
会一路流进报表、流进模型训练集,几周后被业务方发现"这个数字不对",那时
候已经没法回溯到底哪天开始错的、下游哪些结果被污染了。这类事故的挽回
成本比"任务失败"高一个数量级,而平台层面**一行防护都没有**。

典型场景:上游 Kafka 消息某个字段开始传空 → Flink 侧因为类型兼容没报错 →
写进 Iceberg 明细表全是 null → 聚合表数字腰斩 → 看板照常刷新,没有任何
红灯。整条链路上没有一个环节会拦。

**建议做法:**在作业产出之后、下游消费之前插一层断言,失败就阻断而不是
只记日志。行数不为零、主键唯一、关键字段非空比例、数值区间、和昨天比
波动幅度——这几条覆盖绝大多数真实事故。工具上 Great Expectations 偏重、
配置成本高;这个平台已经有 Trino,**用 SQL 表达断言 + 一个统一的执行器**
可能比引入一个大框架更合适,这个取舍要单独定。

**关键设计点:**断言结果要**进数据目录**(OpenMetadata 有 Data Quality
的数据模型),让分析师在查一张表之前就能看到"这张表昨天的质量检查过没过"
——只写进告警通道的话,只有运维看得到,用数据的人看不到,等于白做。

## 2. 数据新鲜度 SLO —— 🟡 检测已做([ADR-070](decisions/070-data-freshness-slo.md)),告警出口未做

做法上有个转向值得记:它**不是**一个新的监控子系统,是数据质量断言再加
一条(理由见 ADR-070)。下面是原始判断,保留。

### 原始判断:监控的对象错了

**现状:**有 kube-prometheus-stack、有 Grafana、有 Alertmanager,但监控
的全部是**组件**(Pod 活着吗、CPU 多少、JVM 堆多大)。

**问题:**数据平台对业务的承诺从来不是"Pod 活着",是"**这张表每小时更新
一次**"。这两件事可以完全脱节:所有 Pod 绿着、所有 Job 显示 Success,
而某张表因为上游没数据已经三天没更新了——现有监控体系**看不见**这件事。

反过来也成立,这个项目已经吃过类似的亏(见 `docs/operations/troubleshooting.md`):
ArgoCD Synced 不等于生效、Pod Running 不等于健康、Job Complete 不等于业务
逻辑跑对。**"组件健康"和"结果正确"之间隔着一层,而告警只装在前面那层。**

**建议做法:**给关键表登记预期更新周期,定时查 Iceberg 表的最新分区/最新
提交时间,超期就告警。指标进 Prometheus,和现有 Grafana/Alertmanager 复用
同一套通道,不另起炉灶。

## 3. 查询审计 —— 🟡 第一段已做(2026-08-23,见 [ADR-066](decisions/066-trino-query-audit.md))

事件已经在往 Kafka 里流了(这就是「不能再晚」的那部分),但**还没落到
Iceberg**,现在只靠 Kafka 保留期兜着。下面是原始判断,保留。

### 原始判断:谁在什么时候查了哪张表,现在查不出来

**现状:**权限侧有 OPA 做**准入**判断(能不能查),但没有配 Trino 的
event listener,**查询本身没有留痕**。

**为什么这是硬要求而不是加分项:**涉及个人信息的数据平台,《个人信息
保护法》要求处理活动可追溯。出了数据泄露要能回答"谁导出过这张表";
员工离职要能回答"他走之前碰过什么"。**这个能力做不到追溯补齐**——没记
就是没记,事后再装 event listener 也拿不回历史。这一点和别的缺口不一样,
别的可以晚点做,这个晚做一天就永久少一天记录。

**建议做法:**Trino event listener 把查询事件落到 Iceberg 表里(平台自己
就有存储,不需要外部系统),然后这张表本身按最严格的权限管起来。顺带
它还能回答"哪些表其实没人用"——`docs/BACKLOG.md` P5 那个"项目瘦身审计"
需要的正是这类数据。

## 4. 成本归属 —— 🟡 配置完成未部署([ADR-069](decisions/069-cost-attribution.md))

### 原始判断:和 ADR-064 是一体两面

**现状:**没有任何成本可见性。

**关系:**[ADR-064](decisions/064-role-based-resource-quota.md) 解决的是
"**能用多少**"(事前配额),这一条解决的是"**实际用了多少、值不值**"
(事后账单)。只有配额没有账单,配额就变成一场纯粹的办公室政治——每个组
都说自己不够用,没有数据支撑谁该多分。

**建议做法:**OpenCost(CNCF,Kubecost 的开源内核)按 namespace/label 出
成本,和 Kueue 的队列标签对齐,这样"哪个组花了多少"是同一套维度。

**给你的现实提醒:**你现在这台按量付费云主机的账单就是这个问题的缩影
——本会话已经因为空转烧掉过约 ¥25。真到多机器多团队,没有归属就是一笔
糊涂账。

## 5. Schema Registry —— 🟡 manifest 完成未部署([ADR-068](decisions/068-schema-registry.md),选的 Karapace)

### 原始判断:上游改字段,下游炸

**现状:**Kafka 部署了,但**没有 Schema Registry**;Flink 作业里 schema
是**写死在 SQL 里**的。

**后果:**上游改一个字段名或类型,消费端只有在运行时才知道,而且(这个
平台实测过)**报错位置往往离根因隔着一两层**——ADR-062 里那个
`ignore-parse-errors` 的坑就是这类:解析失败静默变 null,两个算子之后
才以完全不相干的报错炸出来。

**建议做法:**Kafka 侧上 Schema Registry 做兼容性校验(只允许向后兼容的
变更),生产端和消费端都从 registry 拿 schema,不再各写一份。

## 6. 门户改工作台 —— 🟡 代码完成未上集群([ADR-067](decisions/067-portal-as-workbench.md))

### 原始判断(zhenghe 已经指出 UI 和功能都不好)

**现状:**`apps/platform-portal/src/app.py` 一共 230 行,HTML/CSS 内联在
`render_template_string` 里,本质是**一个带 SSO 的链接目录**——它唯一
超出书签栏的能力是现场探测各工具在不在线。

**问题不在 UI 好不好看,在于它不回答用户真正的问题。**一个分析师打开门户
想知道的是:我有哪些表的权限?我的审批到哪一步了?我昨天那个任务跑成功
了吗?我们组配额还剩多少?——这些**平台里全都有数据**(IAM 表、审批后端、
Argo、以后的 Kueue),只是没有一个地方把它们按"人"聚合起来。现在的做法
是让人自己去五个系统里各翻一遍。

**所以这一条要排在后面做,不是因为不重要,是因为它的价值依赖前面几条**
——门户要显示"配额还剩多少"得先有 ADR-064,要显示"这张表质量如何"得先
有第 1 条。**先做门户只会做出一个更好看的链接目录。**

## 明确不建议现在做的

- **换调度器(YuniKorn/Volcano)**:理由见 ADR-064,集群和 Codex 项目共用。
- **服务网格**:这个规模上纯粹是负担。
- **多集群/跨可用区**:单集群的基本盘(上面这几条)都没夯实之前谈这个是
  本末倒置。
