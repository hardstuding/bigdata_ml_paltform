## 先给结论

最近的工作推进很快，真实跑通了不少链路，也愿意记录失败和未验证项，这是优点。但当前最主要的问题不是“功能还不够多”，而是：

1. **部分核心能力只有流程和演示，没有形成真正的安全闭环。** 权限申请、审批、到期回收已经有了，但 Trino 仍是 `AllowAllAccessControl`；审批结果目前不能阻止未授权用户查数据。
2. **“一键拉起、改配置即可上生产”还没有在仓库结构上成立。** `cloud-full/prod` 主要是说明文档，实际仍要移动 Application 文件、手调资源、按顺序运行许多脚本。
3. **云端实施顺序缺少成本门禁。** 本地镜像未准备完成就开按量 ECS，已经造成用户明确指出的空转成本；当前状态文档也出现了刚写完就与代码不一致的情况。
4. **自建业务代码缺少工程化底座。** 三个 Flask 工具没有自动化测试，源码与 ConfigMap 各维护一份，Pod 启动时在线 `pip install` 且不锁版本。这些都不适合生产级交付。
5. **破坏性操作缺少统一防护。** 历史会话已经真实发生过误删 `data` namespace，最近又直接删除多个 namespace、强杀 Pod/容器来释放内存；仓库尚未把这类教训变成可复用的上下文检查、目标白名单和备份门禁。

建议 Claude 暂停继续横向增加新组件，先按下面 P0 → P1 的顺序收口。除非用户明确改变优先级，不要一边做 cloud-full 部署一边继续发散新功能。

## P0：继续 cloud-full 前必须完成

### P0-1 建立按量资源的“开机前门禁”和可暂停点

**问题证据**

- 最近会话中，ECS 在本地 amd64 镜像缓存只完成一小部分时就已开机，用户明确反馈在浪费费用。
- `environments/cloud-full/STATUS.md` 记录缓存仍未完成，但下一步曾设计成“等全部缓存完成后再继续”，没有在开机前形成可执行的 ready/no-ready 判定。
- 状态文档还写着远程加载脚本“目前没有专门版本”，但仓库已经存在 `scripts/22-load-image-cache-remote.sh`，说明人工维护的状态很容易立即漂移。

**建议 Claude 实施**

1. 新增一个只读的 `cloud-full-preflight.sh`，至少检查：
   - 本地 manifest 中期望镜像数、实际 tar 文件数、缺失项；
   - 每个缓存文件可读且 gzip 完整；
   - SSH、磁盘剩余空间、目标架构、远端 Docker/k3s 状态；
   - 当前任务队列中是否至少有一项能立刻在云端执行；
   - 预计上传量、按当前速率的预计耗时和实例预计费用。
2. preflight 不通过时明确输出 `NOT READY — 建议保持实例停机`，不要启动或建议用户启动按量资源。
3. 将云端流程拆成可恢复的阶段，并保存机器可读状态，例如：`preflight → bootstrap → transfer → load → argocd → roots → configure → verify`。每阶段幂等、失败后可续跑。
4. 每次进入超过 10 分钟的本地等待期，主动给出“云端仍有工作 / 建议停机”的判断；不要只说“继续等”。
5. 修正 `STATUS.md` 中与 `scripts/22-load-image-cache-remote.sh` 冲突的内容；状态最好由脚本生成摘要，人工文档只解释异常和下一步。

**验收标准**

- 在 ECS 停机状态下能完整运行 preflight，结果能明确判断是否值得开机。
- 缺 1 个镜像、缓存损坏、架构不一致、远端空间不足时都会失败，而不是带病继续。
- 中断上传或部署后重跑不会重复已完成的大步骤。
- `STATUS.md`、实际文件和远端状态无互相矛盾的描述。

### P0-2 把“审批完成”变成“访问真的受控”

**问题证据**

- ADR-051 明确写着 Trino 当前仍是 `AllowAllAccessControl`。
- `docs/usage-guide.md` 和权限门户页面也明确承认：即使没有批准，用户目前仍能连接 Trino 查询。
- 因此“目录浏览 → 申请 → 审批 → grant 写回”虽然流程跑通，但不能作为权限系统完成的验收结论。

**建议 Claude 实施**

1. 不要直接从 allow-all 一步切到 fail-closed。先实现可观测的迁移方案：
   - 盘点真实 Trino 查询主体、服务账号、Superset 数据源和当前使用表；
   - 生成“如果现在启用 OPA，哪些请求会被拒绝”的差异报告；
   - 为服务账号和存量业务生成有审计记录的 bootstrap grants；
   - 准备一条经过验证的一键回滚路径。
2. 如果 Trino 插件不支持真正的 shadow mode，不要在文档里把“只开 OPA 日志但 Trino 不调用 OPA”称为影子模式。可以做回放验证：从 Trino audit/query log 提取主体与表，离线送给 OPA 计算预期结果。
3. 在 cloud-full 上安排用户在场的切换窗口，执行：正向授权、未授权拒绝、过期回收、Superset 服务账号、管理员 break-glass、OPA 不可用时行为等端到端测试。
4. 明确 OPA 的故障策略。生产级权限控制通常应 fail-closed，但同时必须有高可用副本、健康检查、告警和经过审计的 break-glass 路径，不能只有单副本 128Mi 的演示部署。

**验收标准**

- 用户 A 有有效 grant 时能查指定表，无 grant、过期 grant、跨用户 grant 时均被 Trino 实际拒绝。
- Superset 和平台服务账号在最小权限下仍能工作。
- OPA 不可用、同步拿不到 Git 仓库、grants 数据格式错误时的行为明确且有告警。
- 回滚在规定时间内完成，并有一次真实演练记录。

### P0-3 为破坏性集群操作加硬性防护

**问题证据**

- 历史 Claude 会话中真实发生过本想删除 `airflow`、却误删 `data` namespace 的事故。
- 最近为释放本地内存又直接删除 namespace、`--force --grace-period=0` 删除 Pod，并在 Docker 层杀容器。
- 当前默认 kubeconfig 指向本地，cloud-full 通过另一份 kubeconfig + SSH tunnel 访问，操作错集群的风险很现实。

**建议 Claude 实施**

1. 新增统一的集群操作 guard，所有会修改/删除资源的运维脚本必须先校验：
   - kube context、API server 地址、集群唯一标识；
   - 目标环境（local-lite/cloud-full/prod）；
   - 允许操作的 namespace 白名单；
   - 目标资源解析后的精确列表。
2. 禁止用裸 `kubectl delete namespace ...` 作为“临时清理手段”。park 组件应通过 GitOps 开关或明确的环境 overlay 完成。
3. 对 namespace/PVC/数据库相关删除，默认要求：预览、备份状态检查、显式环境确认；prod 永不自动确认。
4. 把 cloud-full kubeconfig context 重命名为醒目的名称，并让脚本强制接收 `--environment` / `--context`，不依赖当前默认值。
5. 为误删事故补一份短小的事故复盘：触发条件、影响、恢复过程、已经落地的防复发控制。不能只把事故留在对话里。

**验收标准**

- 在错误 context 上运行 destructive 脚本会在任何写操作前退出。
- 目标不在白名单、目标集合为空或比预期更多时都会退出。
- local-lite park 不再需要删除 namespace 或直接杀 Docker 容器。
- 至少做一次 dry-run 演练证明 guard 真能挡住误删 `data`。

### P0-4 固化 cloud-full 基础设施版本和数据盘选择

**问题证据**

- `scripts/21-bootstrap-cloud-vm.sh` 使用 `curl ... | sh` 安装“当时最新”的 Docker/k3s，没有固定版本，也没有校验下载内容；这与离线 IDC、可复现部署和供应链安全目标冲突。
- 数据盘选择逻辑是“第一个无文件系统的 nvme 设备”，而注释写的是“容量最大的盘”，代码和意图不一致。在多块空盘时可能格式化错盘。
- 脚本包含 `mkfs.ext4 -F`，这是不可逆操作，但缺少设备序列号/容量/云盘标识的强校验。

**建议 Claude 实施**

1. 固定并记录 Docker、k3s、cri-dockerd（如适用）的版本和校验值；优先使用已下载、校验过的安装包，支持内部镜像源。
2. 数据盘改为必须显式传入设备标识，自动探测只用于给出候选列表，不能自动格式化。
3. 格式化前校验：设备不是根盘、无分区/文件系统/挂载点、容量符合预期、序列号符合用户选择；输出完整预览。
4. 将“bootstrap 需要访问哪些外部地址、如何替换为内网源”形成依赖清单，为未来 IDC 演练断网安装。

**验收标准**

- 两次重建得到相同的 Docker/k3s 版本。
- 有两块空盘时脚本不会自行挑一块格式化。
- 完全断开境外网络、只给定本地安装包/内网源时，基础环境仍能装起来。

## P1：生产化收口

### P1-1 真正实现环境画像，而不是移动文件和手工改资源

**问题证据**

- `docs/architecture.md` 已承认 `environments/cloud-full/`、`prod/` 主要还是资源规划说明。
- `cloud-full/STATUS.md` 的待办仍包括把 `pending-definitions` 手工 `git mv` 到 `apps/definitions`，以及手工调大每个组件的 resources。
- 这不满足“改配置即可从 local-lite 切到 cloud-full/prod”，也容易把为 cloud-full 的修改直接影响 local-lite。

**建议 Claude 实施**

1. 先为环境选择一种明确机制（例如 ApplicationSet + 每环境 values、或 Kustomize overlays），不要继续靠移动文件表示开关。
2. 把以下内容都变成环境输入：启用组件、资源 requests/limits、副本数、存储类/容量、域名/TLS、外部依赖地址、镜像仓库前缀、离线策略。
3. local-lite/cloud-full/prod 应能同时存在于 Git 中，不需要为了部署一个环境而改动另一环境的定义。
4. CI 对三个环境分别渲染并校验。

**验收标准**

- 一条明确命令能渲染三个环境，且无手工移动文件。
- cloud-full 调大资源不会改变 local-lite 渲染结果。
- prod 能在不复制整套 Application YAML 的前提下配置多副本、真实域名、存储类和外部基础设施。

### P1-2 给三个自建工具补测试、构建和单一源码

**问题证据**

- 仓库没有发现 Python/Flask 自动化测试。
- `permission-request-app` 已超过简单 demo 范围，包含审批状态机、去重、回收、Git 写回、外部 OA/企业微信、OpenMetadata 查询等关键逻辑。
- 每个自建工具的 `src/app.py` 与 `manifests/app-configmap.yaml` 都各存一份代码，并要求人工同步，天然会漂移。
- Deployment 在 Pod 启动时运行未锁版本的 `pip install flask requests`，部分还运行 `apt-get install git`；断网、PyPI 新版本或包下架都会导致重启失败。

**建议 Claude 实施**

1. 把审批状态机、组织树、grant 到期、OPA 数据转换、OpenMetadata 字段解析抽成可测试的纯函数/模块。
2. 至少补：单元测试、数据库迁移测试、API 鉴权测试、并发/幂等测试、外部依赖超时与失败测试。
3. 只保留 `src/` 为源代码；ConfigMap 由构建脚本生成并在 CI 校验无漂移，或更推荐构建固定 digest 的应用镜像。
4. 引入锁定依赖（含 hash）和非 root、只读文件系统、固定 UID、健康检查、资源限制。
5. 不要在生产 Pod 启动路径中在线 apt/pip 安装。

**验收标准**

- 修改 `src/app.py` 后若部署产物未更新，CI 会失败。
- 无网络环境下 Pod 能正常重启。
- 审批链去重、越级审批、重复回调、到期回收、Git 冲突至少各有测试。
- 镜像按 digest 部署，并能生成 SBOM/依赖清单。

### P1-3 扩大 CI：从“能渲染”升级为“能阻止明显回归”

**问题证据**

- 当前 GitHub Actions 只有 `scripts/validate-charts.py`，主要验证 Helm template。
- 最近仍连续出现 DAG import、Secret namespace guard、NetworkPolicy、探测协议、ConfigMap subPath 等真实 bug，说明现有 CI 覆盖不足。

**建议 Claude 实施**

CI 至少增加：

1. Python compile/lint/test，Airflow DAG import test；
2. shellcheck + 脚本最小行为测试；
3. 所有纯 YAML 的 schema 校验（kubeconform 等）和三个环境的完整渲染；
4. Rego test；
5. ConfigMap 生成物漂移检查；
6. Secret/私钥/高熵凭据扫描；
7. 镜像 tag/digest、依赖锁和禁止生产启动时联网安装的策略检查；
8. 可选的 kind/k3d smoke test，验证 namespace、NetworkPolicy、Job/DAG 基础启动。

**验收标准**

- 人为制造一次 DAG import 错误、ConfigMap 漂移、YAML schema 错误、OPA 测试失败和疑似密钥，CI 都能挡住。
- CI 输出能指向具体文件和原因，而不是只返回一个笼统失败。

### P1-4 收敛“一键拉起”入口和文档真实性

**问题证据**

- README 说“GitOps 是唯一操作接口”“没有隐藏手动步骤”，但同一文档又列出许多必须运行的命令式初始化/修复脚本。
- `scripts/07-fix-trino-liveness-probe.sh` 每次 Deployment 重建后都要重跑，说明修复没有进入期望状态定义。
- cloud-full 目前要人工串联 00/01/02/03/04/16/21/22 等脚本，容易漏步骤，也无法统一恢复。

**建议 Claude 实施**

1. 增加一个总入口（如 `platformctl bootstrap --environment cloud-full`），内部调用分阶段脚本并记录结果；不要让用户记编号顺序。
2. 把可以声明式化的修复放回 Helm values/manifests，不保留“每次重建都手工修”的脚本。
3. 把人工凭据收集集中在部署前 preflight，明确哪些可自动生成、哪些必须人工提供、哪些可稍后补。
4. README 改成准确表述：GitOps 管理哪些期望状态、哪些初始化目前仍是命令式、为什么、重建时如何自动补偿。

**验收标准**

- 从空集群到核心平台，只需一个总入口加一次集中式人工凭据阶段。
- 任意阶段失败后重跑总入口能续跑。
- 删除并重建 Trino Deployment 后不需要运行 `07-fix-*` 才能健康。

### P1-5 镜像缓存要可校验、可增量、可用于真正离线部署

**问题证据**

- 现有远程加载脚本能 rsync 和 `docker load`，但 manifest 未见 sha256/大小/平台校验；加载失败也只打印，不一定让整体失败。
- 项目仍有 runtime apt/pip、GitHub raw grants 同步、在线 chart/安装脚本等网络依赖，因此“镜像已缓存”不等于“IDC 可离线拉起”。

**建议 Claude 实施**

1. manifest 记录 image reference、resolved digest、platform、文件名、字节数、sha256。
2. 上传前后都校验；缺失、损坏或 `docker load` 失败时整体非零退出。
3. 对镜像清单做依赖闭包检查，包括 initContainer、Job、hook、operator 产生的下游镜像。
4. 增加真正的 offline smoke test：断开外网，从空节点用缓存和本地安装包完成核心部署。
5. 长期应引入内部 registry；tar cache 适合作为引导/灾备介质，不应成为多节点生产的主要镜像分发方式。

**验收标准**

- 任意 tar 被截断或替换后，传输/加载在部署前失败。
- 断网重建不会出现 ImagePull、pip、apt、GitHub raw、Helm repo 等外部依赖。

## P2：上述完成后再继续的能力

以下并非不重要，但不建议抢在 P0/P1 前继续扩展：ClickHouse、新的 Notebook 产品形态、更多通知渠道、更多门户页面、更多治理组件。先把已有 Trino/Iceberg/审批/建表/dbt/Notebook 链路做成稳定、可测试、可重建的生产基线，再讨论新增组件，避免平台越做越宽、每条链路都停在 MVP。

## 多角色产品能力评估：当前还不能算完整平台

当前项目已经是覆盖面较广、许多链路经过真实验证的“平台原型/集成验证环境”，但还不能称为让数据分析师、大数据开发、算法、运维和管理岗都觉得好用、好管、好扩展的生产级平台。

需要特别纠正一种判断方式：**组件已经部署、API 已经打通、Demo 已经运行，不等于对应岗位已经获得可日常使用的产品能力。** 后续规划应从“再接入哪个开源组件”转为“一个角色完成一项工作还缺哪些环节”。

### 各角色当前完成度

| 角色 | 当前已有 | 关键缺口 | 当前判断 |
|---|---|---|---|
| 数据分析师 | Trino、Superset、dbt MVP、表目录、权限申请 | 缺成熟 SQL/Notebook 工作台、项目空间、查询保存与分享、结果导出、定时任务、指标管理，以及真正执行的数据权限 | 可演示，日常体验不完整 |
| 大数据开发 | Airflow、Spark Operator、SeaTunnel、Kafka、Iceberg、部分血缘 | 缺统一开发工作台、代码/分支/发布流程、任务模板、配置与 Secret 管理、测试环境、数据质量、补数重跑、完整实时链路 | 技术组件较多，开发平台未成型 |
| 算法工程师 | JupyterHub、MLflow、KServe、Feast、Argo Workflows | 缺稳定 Notebook 镜像、依赖环境管理、GPU/训练队列、数据集版本、训练任务提交、模型审批发布、推理监控和回滚 | Demo 链路，不是完整 MLOps |
| 运维 | ArgoCD、Prometheus、Grafana、Loki、备份、NetworkPolicy、资源配额 | 缺统一运维控制面、告警处理闭环、SLO、容量/成本管理、升级回滚自动化、灾备演练、多节点高可用、危险操作保护 | 有运维工具，缺成熟运维体系 |
| 管理岗 | 组织架构、审批链、部分审计、平台门户 | 缺成本、资源、项目、活跃度、任务成功率、SLA、数据资产、权限风险、模型服务等管理看板 | 当前最薄弱，几乎没有管理驾驶舱 |
| 平台管理员 | Keycloak SSO、IAM 同步、建表和权限门户 | 缺完整租户/项目管理、角色授权矩阵、策略配置、服务目录、生命周期管理和自助运营后台 | 部分可用，配置仍高度代码化 |

### 综合判断

按当前仓库状态粗略评估（不是精确 KPI，只用于纠正“是否已经完成”的预期）：

| 维度 | 评分（10 分制） |
|---|---:|
| 技术选型与组件覆盖 | 7 |
| 核心链路验证 | 6 |
| 数据分析师体验 | 3 |
| 大数据开发体验 | 3 |
| 算法工程体验 | 4 |
| 运维管理成熟度 | 4 |
| 管理岗能力 | 2 |
| 生产可用性 | 3 |
| 架构扩展方向 | 6 |
| 新增能力的实施成本 | 3 |

因此后续既不能只做工程收口，也不能继续横向堆组件。正确路线是：**用 P0/P1 建立可靠底座，同时围绕角色工作流纵向完成产品闭环。**

## 后续五条产品建设主线及大致实现方案

这五条主线是对 P0/P1 工程任务的补充。P0/P1 解决“平台能否可靠运行和持续交付”，以下内容解决“不同岗位是否真的能用”。建议 Claude 把它们写进正式 backlog/roadmap，每项维护 `未开始 / 设计中 / 已实现 / 静态验证 / 集群验证 / 用户验收` 状态。

### 产品主线 A：统一开发工作台

**目标用户**：数据分析师、大数据开发、算法工程师。

**目标体验**：用户登录一个入口，进入所属项目空间，在同一套项目/权限语义下使用 SQL、Notebook、任务和发布能力，而不是自己理解十几个开源组件之间如何跳转。

**建议实现方案**

1. **先统一项目模型，不急着自研大前端**：
   - 定义 `Project`：项目 ID、名称、负责人、成员及角色、Git 仓库、Trino catalog/schema、对象存储前缀、K8s namespace、资源队列、成本中心。
   - 项目模型先以声明式 YAML/数据库存在，由一个 project-controller 或管理服务同步到 Keycloak Group、K8s RBAC/namespace/quota、Trino/OPA、MinIO 和各工具。
   - 避免每个系统各维护一套“项目”和成员关系。
2. **SQL 工作区**：
   - 短期可评估复用现有成熟 SQL 编辑器能力，不要立刻自研查询引擎；平台门户提供统一入口和项目上下文。
   - 至少支持查询历史、收藏、分享、结果下载、运行中止、资源组/队列选择、表字段快捷查看。
   - 查询统一走个人身份，不能所有用户共享一个 Trino 服务账号，否则审计和权限失效。
3. **Notebook 工作区**：
   - 以 JupyterHub 为基础，提供平台维护的镜像模板：分析、Spark、算法训练三类；镜像固定版本并经过测试。
   - 用户可选择 CPU/内存/GPU 规格、项目和环境；持久化工作目录，自动挂载项目配置，但 Secret 通过动态凭据/Secret 引用提供，不写进 Notebook。
   - Notebook 中预装 Trino、Spark、Iceberg、MLflow、Feast SDK 和使用示例。
4. **任务与发布**：
   - 一个 Git 项目同时容纳 SQL/dbt、Airflow DAG、Spark/SeaTunnel 作业和测试。
   - 建立 dev → test → prod 流程：PR 校验、测试数据运行、审批、部署、回滚。
   - Airflow/Argo Workflows 作为执行后端，门户只做统一提交、状态聚合和深链接，不复制它们的调度能力。
5. **先做薄控制面**：
   - 自建层负责统一项目、模板、权限和状态聚合；编辑器、Notebook、调度、查询执行继续复用成熟组件。
   - 不要再次出现一个几百行单文件 Flask 同时承担 UI、数据库、审批和外部系统集成。

**阶段交付**

- A1：项目模型 + 一键创建项目空间。
- A2：分析师 SQL/Notebook 黄金路径。
- A3：大数据作业模板 + CI/CD。
- A4：算法 Notebook → 训练任务 → 模型发布黄金路径。

**验收场景**

- 新分析师加入项目后，不接触 Kubernetes/YAML，能在 30 分钟内完成找表、申请、查询、保存、分享和制作一个 Superset 图表。
- 大数据开发从模板创建 Spark/SeaTunnel 作业，经测试环境验证后发布，失败能定位日志并重跑。
- 算法工程师能从 Notebook 提交可复现训练，而不是让 Notebook 本身长期占资源跑训练。

### 产品主线 B：数据资产与治理闭环

**目标用户**：数据分析师、大数据开发、数据治理、平台管理员、管理岗。

**建议实现方案**

1. OpenMetadata 作为资产、字段、owner、标签、血缘和质量结果的主要元数据底座，避免自建门户再存一套重复目录。
2. 建表工具升级为“数据产品/数据契约”入口：表结构、说明、owner、分级、生命周期、质量规则、SLA、分区和变更策略一次提交。
3. 权限系统完成闭环：目录浏览 → 申请 → 分级审批 → OPA 真正执行 → 到期提醒/回收 → 审计。
4. 对敏感字段建立分类和策略映射，逐步实现列隐藏、列脱敏、行过滤；先从少量明确场景落地，不一次设计万能规则语言。
5. 血缘覆盖 dbt、Airflow、SeaTunnel、Spark、Trino 查询；所有来源进入 OpenMetadata，门户只展示汇总。
6. 数据质量优先接入关键表规则、运行结果和告警；明确 owner 收到什么通知、失败如何确认和关闭。
7. 增加表变更/下线流程：影响分析、消费者确认、过渡期和最终删除，避免只有“建表”没有生命周期结束。

**阶段交付**

- B1：权限真实执行和审计闭环。
- B2：数据契约 + 核心表质量规则。
- B3：端到端血缘和变更影响分析。
- B4：敏感字段识别与行列级策略。

**验收场景**

- 未授权用户实际查询失败，审批后无需人工改系统即可成功，到期后自动失败。
- 某字段变更前能列出受影响的 dbt 模型、Airflow/Spark 作业和 Superset 看板。
- 数据质量失败能自动通知明确 owner，并能在统一位置看到处理状态。

### 产品主线 C：完整 MLOps

**目标用户**：算法工程师、算法负责人、模型运维。

**建议实现方案**

1. **环境可复现**：维护经过批准的训练/推理基础镜像；项目用锁文件声明依赖，CI 构建项目镜像，禁止临时 `pip install latest` 作为正式运行方式。
2. **训练任务化**：Notebook 用于探索；正式训练转换为 Argo Workflow/Kubernetes Job，记录代码 commit、镜像 digest、参数、数据集版本、特征版本和随机种子。
3. **实验和模型治理**：MLflow 记录实验；模型注册时补齐 owner、用途、指标、数据版本、风险等级和审批状态。
4. **发布流程**：模型注册 → 自动验证 → 人工审批（按风险可选）→ KServe canary → 指标观察 → 全量/回滚。
5. **在线监控**：至少覆盖请求量、延迟、错误率、资源、输入特征统计、预测分布；有真实标签后再做效果/漂移闭环。
6. **Feature Store**：Feast 先服务一个真实用例，验证离线/在线一致性、回填、TTL 和权限，再决定是否推广，避免只保持 Demo。
7. **GPU/队列**：通过 node labels/taints、ResourceQuota、PriorityClass 和调度策略隔离探索、训练和推理；没有 GPU 硬件前先把接口和资源模型设计好，不伪造已验证状态。

**阶段交付**

- C1：标准镜像 + 可复现训练任务。
- C2：模型审批、灰度和回滚。
- C3：推理可观测性。
- C4：真实特征服务与漂移/效果监控。

**验收场景**

- 另一名算法工程师仅凭 run metadata 能复现同一训练结果。
- 一个坏模型能在灰度阶段被指标阻止，并一键回滚到上一版本。
- Notebook 关闭后正式训练任务不受影响，且资源用量可追踪到项目。

### 产品主线 D：统一运维控制面

**目标用户**：平台运维、大数据运维、值班人员。

**建议实现方案**

1. 定义服务目录：组件 owner、依赖、SLO、Dashboard、Runbook、版本、备份等级、维护窗口。
2. 监控从“有 Prometheus/Grafana”升级为四层视图：基础设施、平台组件、数据/训练任务、用户黄金链路。
3. 告警必须进入闭环：触发、路由、认领、处理、恢复、复盘；未配置真实通知渠道时不能称为完整告警能力。
4. 建立 SLO：登录、Trino 查询、任务提交、调度成功、Notebook 启动、模型推理等关键路径。
5. 做容量和成本管理：namespace/project/队列资源利用率、空闲资源、失败重试消耗、云实例费用和预算告警。
6. 统一 day-2 操作：启停、扩缩容、证书、升级、回滚、备份、恢复；每项有 preflight、dry-run 和审计。
7. cloud-full 验证多节点和故障场景后，再声明生产高可用；单节点 cloud-full 只能验证集成，不代表 HA。

**阶段交付**

- D1：服务目录 + 黄金链路 Dashboard/告警。
- D2：统一 Runbook 和安全运维入口。
- D3：容量/成本看板与预算告警。
- D4：多节点故障、备份恢复和升级回滚演练。

**验收场景**

- 值班人员收到“分析查询不可用”时，能从一个入口定位是 SSO、Trino、OPA、Hive Metastore 还是对象存储故障。
- 平台能展示每项目资源与成本，发现长期空闲 Notebook 和异常重试任务。
- 恢复演练以 RPO/RTO 验收，而不是只确认备份文件存在。

### 产品主线 E：管理驾驶舱

**目标用户**：技术负责人、数据负责人、算法负责人、部门管理岗。

**建议实现方案**

1. 不为管理看板另造一套数据源。将 ArgoCD/Kubernetes、Prometheus、Airflow、Trino、OpenMetadata、MLflow/KServe、IAM/审批等数据汇总到管理指标层。
2. 第一版只回答管理者真正需要的少量问题：
   - 平台和关键业务链路是否健康；
   - 哪些团队/项目在使用，资源和费用是多少；
   - 作业成功率、SLA、积压和高频故障；
   - 数据资产数量、owner 覆盖、质量和血缘覆盖；
   - 敏感数据授权、长期权限和即将过期权限；
   - 实验、注册模型、在线模型及服务健康度。
3. 指标必须定义口径、owner、刷新频率和数据来源；不能只做漂亮但不可解释的图表。
4. 按角色控制管理视图：部门负责人只看本部门，平台管理员可看全局；管理驾驶舱本身也要经过权限和审计。
5. 可以优先复用 Grafana/Superset 出第一版，不必先开发新的前端；当交互、权限和工作流需求证明确实超出后再自研。

**阶段交付**

- E1：平台健康、使用量、成本和任务 SLA 看板。
- E2：数据治理和权限风险看板。
- E3：算法实验与在线模型看板。

**验收场景**

- 管理者不查看 Pod/namespace，也能判断平台健康、投入产出、主要风险和需要谁处理。
- 看板中的每个指标都能下钻到项目、owner 和原始系统证据。

## 跨角色产品设计原则

1. **统一身份不等于统一体验**：SSO 只解决登录；还要统一项目、角色、资源、资产和审计语义。
2. **门户不是链接导航页**：短期可作为导航，但长期应成为项目和工作流控制面；专业操作仍深链接到成熟工具。
3. **一个事实只有一个权威来源**：组织成员、资产、实验、调度状态分别选择权威系统，门户做聚合，不复制出多份最终一致性问题。
4. **默认自助，例外审批**：低风险操作通过配额和策略自动完成；高风险、生产变更和敏感数据才进入审批。
5. **每条能力必须有黄金路径**：用一个具体角色从头走到尾验收，不能只按组件逐个检查 Running。
6. **所有资源能归属到项目/owner/成本中心**：这是权限、成本、运维和管理看板共同的基础。
7. **先薄集成，后有证据地自研**：优先复用成熟组件；只有跨系统语义、项目控制和企业流程由平台自建。

## 路线优先级建议

不建议五条产品线同时铺开。推荐顺序：

1. **可靠底座**：完成 P0，尤其是成本门禁、危险操作保护、权限实际执行。
2. **项目模型**：为所有角色建立统一项目/成员/资源/成本归属。
3. **分析师黄金路径**：资产搜索 → 申请 → SQL/Notebook → dbt → Superset，最容易验证平台是否真的好用。
4. **大数据开发黄金路径**：模板 → 测试 → 发布 → 调度 → 质量/血缘 → 运维。
5. **算法黄金路径**：Notebook → 可复现训练 → MLflow → 审批 → KServe 灰度/回滚。
6. **运维控制面和管理驾驶舱**：从前三条黄金路径产生的真实指标构建，而不是先造空看板。
7. **新增引擎**：只有现有引擎无法满足经过量化的负载需求时，再评估 ClickHouse 等组件。

每条黄金路径应先选一个小而真实的业务用例完成，不要同时覆盖所有场景。完成标准是用户任务成功率和可运营性，不是新增了多少 YAML/ADR。

## 为后续交接给 Codex/其他维护者准备的项目规范

用户预计先让 Claude 继续工作一段时间，之后可能交接给 Codex。为了避免再次依赖超长聊天记录，Claude 从现在起应把交接能力当成正式交付物。

### 仓库内必须长期维护的交接材料

1. **`environments/<env>/STATUS.md`**：只写当前事实、阻塞、下一步和最后验证时间；易变状态不得散落到多个 ADR。
2. **统一 backlog/roadmap**：每项包含 ID、目标角色、用户问题、范围、非目标、状态、负责人、依赖、验收标准和证据链接。
3. **能力矩阵**：按角色维护“未开始/设计/实现/验证/用户验收”，避免仅按组件统计完成度。
4. **Runbook**：部署、升级、回滚、备份恢复、启停和常见故障必须能由没参与历史对话的人执行。
5. **验证证据**：命令、测试输入、预期结果、实际结果、时间和环境；日志可生成，不要把大量瞬时输出塞进 ADR。
6. **决策记录**：ADR 只记录长期设计取舍，不承担任务状态和聊天摘要功能。
7. **已知风险和技术债**：说明影响、触发条件、临时绕法和计划修复，不把风险藏在代码注释深处。

### 每次 Claude 结束一段工作前必须更新

1. 当前分支、最后 commit、工作区是否干净、是否已 push。
2. 本地/cloud-full/prod 分别处于什么状态，哪些计费资源仍开着。
3. 后台任务、SSH tunnel、临时端口转发和长时间进程是否仍运行。
4. 实际完成、只写代码、只静态验证、真实集群验证、用户验收分别有哪些。
5. 失败过但尚未解决的事项，以及下一位维护者应从哪条命令/哪个文件继续。
6. 是否做过任何手工集群变更、是否已经回写 Git；不能留下未记录的漂移。
7. 新增的凭据需求和人工步骤，但不得记录真实密钥内容。

### 建议的单项任务交接格式

```markdown
## TASK-xxx 标题

- 目标角色：
- 用户问题：
- 当前状态：未开始 / 设计中 / 已实现 / 静态验证 / 集群验证 / 用户验收
- 本次完成：
- 尚未完成：
- 关键文件：
- 设计决策：
- 验证命令与结果：
- 已知风险：
- 下一步唯一入口：
- 回滚方式：
```

“下一步唯一入口”尤其重要：后续 Codex 接手时应该能执行一个明确命令或打开一个明确文件继续，而不是重新阅读数十 MB Claude JSONL 对话来推断上下文。

### 交接验收

在 Claude 阶段工作结束前，建议做一次“陌生维护者演练”：不依赖 Claude 的会话记忆，仅根据仓库文档，在新终端中完成以下事项：

1. 判断当前 cloud-full 是否应开机；
2. 找到正在进行的主线和下一步；
3. 从中断点恢复部署；
4. 验证一个分析师或开发者黄金路径；
5. 安全回滚一次变更；
6. 查清尚未完成的需求及优先级。

如果其中任何一步必须询问“Claude 当时到底做了什么”，就说明交接材料还不合格。

## 对 Claude 工作方式的具体建议

1. **先读项目记忆和仓库事实，再做资源/架构判断。** “记下来”不等于“决策时用到了”；每次涉及容量、成本、核心原则，应在行动前列出引用的基线。
2. **区分四种完成状态：代码写完、静态验证、真实集群验证、生产闭环。** 对外汇报时明确是哪一层，不要用“完整跑通”概括尚未真正执行访问控制的审批系统。
3. **一次只维护一个当前主线。** 当前主线是 cloud-full，临时想到的门户/dbt/新组件可进入 backlog，除非它直接解除当前阻塞，不要立即切过去实现。
4. **对计费资源先排队、后开机。** 开机前必须说明：立刻执行什么、预计多久、完成后是继续还是停机。
5. **等待期间优先做能减少后续云端耗时的本地工作。** 例如校验缓存、预渲染 manifests、准备离线包、写测试，而不是边等边扩大范围。
6. **高风险动作先给机器可验证的目标清单。** 不要把自然语言里的“清理 Airflow”直接翻译成多条 delete 命令。
7. **文档避免重复维护同一事实。** 当前状态、架构决策、通用操作分别放对地方；可由代码/命令生成的版本、进度、镜像数不要手写。

## Claude 容易失忆、停下和跑偏：建议建立仓库级 AI 执行协议

这三个现象有关联，但原因不同：

- **失忆**：重要要求只存在于聊天上下文、会话压缩摘要或 Claude 私有 memory；即使“记过”，下一次决策也不一定主动读取和应用。
- **容易停下**：长命令被终端/客户端中断、认证或网络失败、上下文切换后丢失后台任务，也可能是 Claude 把一个局部结果误判成整项任务完成。
- **容易跑偏**：当前主线、优先级和禁止扩展范围没有机器可见的约束；Claude 发现一个新想法后立即实现，导致 cloud-full、门户、dbt、内存处理等工作频繁切换。

### 现有机制并非没有，而是没有形成执行闭环

用户在历史对话中已经多次要求 Claude 做类似的记忆、状态和交接建设，不能把本节描述成一个用户从未提过的新建议。最近会话里能确认 Claude 已经做过：

- 在 Claude 项目私有目录维护 `memory/MEMORY.md` 和多份项目 memory；
- 根据用户“核心记住”的要求补了 `project_core_requirements.md`，记录“可交接、一键拉起、改配置可上生产”三条底线；
- 维护 `environments/cloud-full/STATUS.md`，尝试区分当前状态、通用 README 和长期 ADR；
- 把“怀疑遗忘时翻原始 JSONL”“按量资源需要成本意识”等规则写进全局 `~/.claude/CLAUDE.md`；
- 多次在 ADR 中诚实区分已验证和未验证范围。

这些工作是有价值的，问题在于它们主要解决了“信息有没有被写下来”，没有解决以下执行问题：

1. **启动时没有强制读取**：生产容量基线明明已经在 memory/ADR 中，推荐云规格时仍没有使用。
2. **没有唯一当前主目标**：状态和需求存在，但门户、OPA、dbt、cloud-full、内存处理仍频繁互相切换。这里要求的是一个主目标，不是禁止在主目标内部并行执行互不冲突的工作流。
3. **没有完成门禁**：局部实现或验证后容易停下，尚未对照原始需求逐项验收。
4. **状态缺少自动核对**：`STATUS.md` 写着远程镜像加载脚本还没有，但相应脚本已经存在。
5. **私有记忆不能稳定交接**：`~/.claude/projects/.../memory` 和全局 `~/.claude/CLAUDE.md` 不在项目仓库中，Codex、其他开发者、CI 和新机器无法共同依赖。
6. **规则没有和工具绑定**：没有 preflight、task runner、CI 或脚本强制这些规则，仍依赖 Claude 每次“自觉想起来”。

因此本节不是要求推翻 Claude 已经建立的 memory/STATUS/ADR，而是要**整理、去重、迁移权威项目事实到仓库，并把已有规则变成启动检查、执行门禁、任务状态和验收流程**。私有 memory 可以继续保留，但应只作为索引和个人偏好层，指向仓库里的权威内容。

不能指望用一句“你要记住、继续做、不要停”彻底解决。需要把已经提出、部分实现的约束升级成仓库内可共同读取、可验证、能强制执行的工作协议。

### 1. 在仓库根目录增加项目级 `CLAUDE.md`，承接已有全局规则

不要废弃现有 `~/.claude/CLAUDE.md` 和 Claude 私有 memory，但不要只依赖它们：

- 私有 memory 对其他维护者/Codex 不可见；
- 换机器、换工具或交接后容易丢失；
- 即使 memory 中存在，Claude 也可能没有在做决定前检索它。

仓库级 `CLAUDE.md` 应保持短小，写长期强规则，不要塞项目全部知识。建议内容至少包括：

```markdown
# 本项目 AI 协作规则

## 每次开始工作必须按顺序读取
1. CLAUDE.md
2. docs/project/current-work.md
3. docs/project/roadmap.md 中 CURRENT_WORK 引用的任务
4. 当前环境 STATUS.md
5. 当前任务直接引用的 ADR/Runbook

## 核心要求
- 文档和验证证据必须足以让新 AI/人类接手。
- 必须有从空环境可恢复、可重复的一键部署入口。
- local-lite/cloud-full/prod 必须通过配置切换，不能维护三套漂移副本。
- 组件 Running、代码写完、静态验证、集群验证、用户验收是不同状态。

## 执行纪律
- 同一时间只能有一个 CURRENT 主目标；主目标内部可以有多个明确登记的并行工作流。
- 未经用户明确同意，不得因为发现新想法切换主线；只记录到 BACKLOG。
- 修改范围超出当前任务时先停下说明，不得顺手实现。
- 任何高风险、计费或不可逆操作必须执行对应 preflight/guard。
- 不得把 namespace 删除、强杀容器作为常规启停方式。

## 不允许静默结束
- 达到验收标准：更新状态、验证、交接记录后才能结束。
- 遇到阻塞：记录阻塞原因、已尝试内容、下一步；能做同一任务内的安全工作就继续。
- 长任务：持续写日志和状态文件；不能只依赖聊天消息。
```

重要原则应从现有全局规则和 `project_core_requirements.md` 中去重、迁移到项目仓库，作为所有 Agent 共同规则；Claude 私有 memory 只保存个人偏好或指向仓库文档的索引，不保存唯一事实。迁移后不要保留三份互相漂移的规则正文。

### 2. 增加唯一的 `docs/project/current-work.md`

这是防失忆、防跑偏最重要的文件。任何时刻只能有一个 `CURRENT` 主目标，但一个主目标可以包含多个并行工作流。建议格式：

```markdown
# 当前唯一主任务

- Task ID：TASK-xxx
- 标题：
- 目标角色/用户价值：
- 为什么现在做：
- 当前阶段：
- 明确范围：
- 明确非目标：
- 验收标准：
- 当前环境和 context：
- 计费资源状态：
- 并行工作流：ID / owner / 范围 / 文件或环境所有权 / 状态 / 依赖
- 已完成 checkpoint：
- 正在运行的进程（工作流 ID/PID/日志/启动命令）：
- 阻塞：
- 下一步唯一动作：
- 最后更新时间：
```

规则：

1. Claude 每次恢复会话先读它，再执行命令。
2. 用户提出新想法时，默认进入 backlog，不自动替换 CURRENT；只有用户明确说“暂停当前任务，改做这个”才切换。
3. 每完成一个不可忽略的阶段立即更新 checkpoint；不要等会话快结束才补。
4. CURRENT 达到验收标准并留下证据后才允许标记完成，再选择下一项。
5. 如果文件内容与集群/Git 状态冲突，先核实和修正文档，不基于旧状态继续执行。
6. “下一步唯一动作”应理解为主协调路径的下一步；并行工作流各自也必须记录自己的下一动作。

### 2.1 采用“单主线、多工作流并行”，不要退化成完全串行

用户明确期望 Claude 在合适的时候并行工作。并行本身不是跑偏；**脱离同一个主目标、缺少依赖和资源控制的并行才是跑偏。**

建议在 `project/current-work.md` 中为每个并行工作流登记：

| 字段 | 含义 |
|---|---|
| Workstream ID | 例如 `WS-CACHE-VERIFY` |
| 服务的主目标 | 必须指向当前 Task ID |
| owner | Claude 主进程、sub-agent 或后台任务 |
| 范围/非目标 | 防止工作流自行扩张 |
| 文件所有权 | 允许修改的目录/文件，避免并发覆盖 |
| 环境所有权 | local/cloud、kube context、namespace |
| 资源预算 | CPU、内存、网络、云费用或并发上限 |
| 依赖 | 等待哪个工作流或产物 |
| 状态和日志 | 可恢复的真实状态 |
| 合并/验收方式 | 如何回到主目标 |

**适合并行的例子**

- 本地导出/校验 amd64 镜像，同时云端加载已经完成的批次；
- 长时间 rsync 时，本地预渲染 cloud-full manifests、补测试和 preflight；
- 一个 sub-agent 审查 OPA 策略测试，另一个审查环境 overlay 设计，主进程负责整合，但不能同时修改同一文件；
- CI、镜像构建、静态扫描等彼此独立的只读/生成型任务；
- 不同组件的只读诊断，最后由主工作流统一判断。

**不适合并行的例子**

- 两个 Agent 同时修改同一 Application、同一 Flask 文件或同一状态文档；
- 一边删除/park namespace，一边在同一 namespace 部署或验证；
- 一边修改 grants/OPA 策略，一边进行权限切换验收；
- 多个工作流同时对同一个 Git 分支提交、rebase、push，没有明确合并顺序；
- 在内存已经吃紧的 Mac 上同时跑多个重量级镜像构建/集群组件；
- 在按量云资源上启动“可能有用”的并行工作，但没有立即可执行的任务和成本预算；
- 主目标是 cloud-full，却并行开发与其无关的新门户、ClickHouse 或新功能。

**并行调度规则**

1. 默认并行上限为 2～3 个有效工作流；超过上限要说明收益和资源影响。
2. 优先并行只读检查、测试、下载/传输和互不重叠的代码工作。
3. destructive、数据库迁移、权限切换、GitOps 同步等高风险写操作必须由一个主协调工作流串行控制。
4. 每个 sub-agent 只接收有边界、有产物、有验收标准的任务，不允许自行扩展 backlog。
5. 主 Claude 对最终整合负责，不能把多个 sub-agent 的输出未经核验直接宣布完成。
6. 并行任务开始前检查文件冲突、集群目标和本地/云资源；结束后统一跑测试和验收。
7. 某工作流阻塞时，其他独立工作流可以继续；但不得借机切换到无关产品主线。
8. 用户询问进度时，按工作流汇报“运行中/完成/阻塞/费用状态”，而不是只说“还在做”。

**并行工作的验收标准**

- 能说明每个并行工作流如何服务同一个 CURRENT 主目标。
- 没有文件覆盖、集群竞态或资源互相拖垮。
- 任一工作流中断后可独立恢复，不影响其他已完成产物。
- 并行确实缩短关键路径，而不是制造更多在制品。
- 主目标结束时所有工作流都有明确终态：已合并、已验证、已取消或记录为 backlog；不能留下无人管理的后台任务。

### 3. 建立带优先级和变更控制的 `docs/project/roadmap.md`

Claude 跑偏常常不是完全做错，而是把一个合理但不紧急的想法提前做了。Backlog 应让它“记下来但先不做”。每项至少包含：

- ID、目标角色、用户问题；
- P0/P1/P2；
- 是否获用户批准；
- 依赖和预计成本；
- 验收标准；
- 状态；
- 与 CURRENT 的关系。

建议固定规则：

- P0 可以阻断 CURRENT，但要写明阻断依据，例如安全、数据丢失、持续计费。
- 新发现的 P1/P2 不得打断 CURRENT。
- “顺手修一下”如果超过 15 分钟、跨组件或改变架构，必须单独建任务。
- 用户说“尽可能多做”不等于可以无序扩展；仍按已批准优先级逐项完成。

### 4. 把“不能随便停”改成可验证的完成/暂停协议

AI 无法保证进程永不退出，电脑重启、客户端更新、认证、上下文上限和网络故障都可能中断。正确目标不是“永不停”，而是：**即使随时中断，也不会丢进度，恢复后能自动知道从哪继续。**

Claude 只有在以下情况之一满足时才能结束当前工作回合：

1. **完成**：验收标准全部满足，测试通过，状态和交接文件已更新。
2. **需要用户决策**：确实存在会改变结果的选择，已给出选项、影响和推荐；不是把普通技术判断推给用户。
3. **权限/外部阻塞**：需要用户独有的控制台、凭据或外部资源；已完成不依赖该阻塞的同范围工作。
4. **安全停止**：继续会产生不可接受的数据、费用或生产风险。

不应作为停止理由：

- “已经做了不少”；
- 某个局部测试通过；
- 后台任务还在跑但没有保存 PID/日志；
- 发现了另一个更有意思的功能；
- 一个命令失败一次；
- 需要等几分钟但没有设计可恢复的监控。

### 5. 长任务必须托管，不能只挂在 Claude 当前终端

镜像导出、rsync、集群安装和长测试容易因客户端或会话结束而中断。建议统一提供 `scripts/task-runner.sh` 或使用系统已有的可靠机制，至少做到：

1. 每个长任务有 task ID、PID、开始时间、命令摘要、日志文件、退出码文件。
2. 支持 `start/status/logs/stop/resume`，且 resume 必须幂等。
3. Claude 恢复会话时先检查 CURRENT 中记录的所有任务状态。
4. 任务失败时保留最后错误，不用 `|| true` 掩盖失败。
5. 云端传输/部署使用断点续传和阶段 checkpoint。
6. 不让未被管理的 `nohup`、SSH tunnel 和 port-forward 长期残留。

示意状态文件：

```text
.runtime/tasks/TASK-123.env   # PID、状态、开始/结束时间、退出码、日志路径
logs/tasks/TASK-123.log       # 可持续查看的输出
```

`.runtime/` 应加入 `.gitignore`；CURRENT 只记录任务 ID 和可恢复命令，不记录敏感信息。

### 6. 设置固定 checkpoint，而不是依赖 Claude 自觉记忆

建议按事件而非纯时间更新：

- 开始任务前；
- 任何计费资源开/关机后；
- 开始长任务后（记录 PID/日志）；
- 每次 commit/push 后；
- 每个部署阶段完成后；
- 首次失败和解决失败后；
- 进行任何手工集群变更后；
- 会话结束或需要用户输入前。

长时间没有事件时，可每 20～30 分钟写一次简短 heartbeat，但不要为了“看起来没停”在聊天里重复发送“继续等”。heartbeat 应说明进度数字、是否卡住、费用状态和预计下一检查点。

### 7. 每轮开始执行“事实恢复”，不要相信上一轮总结

Claude 会话摘要可以用来定位，但不能直接作为事实。恢复流程应自动检查：

1. `git status`、分支、最近 commit、是否已 push；
2. CURRENT 和环境 STATUS；
3. 当前 kube contexts 和目标集群唯一标识；
4. 计费资源状态（若无法通过 API 获取，明确要求人工确认，不能猜）；
5. task runner 中的后台任务；
6. ArgoCD/Application/关键 Pod 实际状态；
7. 文档宣称的下一步是否已经被代码完成。

这样可以避免类似 `STATUS.md` 说远程镜像加载脚本尚未完成，但代码中已经存在该脚本的漂移。

### 8. 用“需求追踪矩阵”解决用户需求被遗忘

建议新增 `docs/requirements.md`，每条用户需求分配稳定 ID，而不是散落在聊天和 ADR 中：

| 字段 | 含义 |
|---|---|
| Requirement ID | 例如 `REQ-ANALYST-001` |
| 原始需求 | 保留用户语义，不擅自缩小 |
| 目标角色 | 分析师/开发/算法/运维/管理 |
| 验收场景 | 用户如何证明它真的可用 |
| 关联任务 | TASK ID |
| 实现文件 | 代码/配置 |
| 验证证据 | 测试/环境/日期 |
| 当前差距 | 没做完的部分 |
| 状态 | 未规划/进行中/部分完成/已验收 |

Claude 每次说“这个需求完成了”之前，必须更新矩阵并逐条对照验收场景。这样能防止把“部署了 JupyterHub”误当成“算法开发平台完成”，或把“审批记录写入 Git”误当成“权限已经生效”。

### 9. 给用户一个可重复使用的控制指令

用户以后可以直接给 Claude 下类似下面的指令，减少解释成本：

```text
继续 CURRENT_WORK，不切换主线。
开始前先按 CLAUDE.md 做事实恢复，并汇报：当前任务、验收标准、下一步、
后台任务、计费资源状态。

新发现的问题先写 BACKLOG；除非属于数据安全、持续计费或会阻断当前任务的
P0，否则不要立即实现。

不要在局部结果后结束。只有达到 CURRENT_WORK 的完成/暂停条件，更新状态、
验证证据和交接记录后才可以停。如果发生中断，确保恢复时可以从唯一入口续跑。
```

这条指令不能替代仓库协议，但可以强制 Claude 每轮重新对齐。

### 10. 不建议采取的办法

- 不要无限扩大 Claude 的聊天上下文；内容越长不代表更会抓住重点。
- 不要把所有历史聊天全文复制进 `CLAUDE.md`。
- 不要只依赖 Claude 私有 memory；项目事实必须在仓库内。
- 不要用“全自动、不要问、一直做”解除危险操作确认；这会放大跑偏和误删风险。
- 不要同时给十几项同优先级需求又期待它严格按隐含顺序执行。
- 不要靠频繁聊天催促长任务；应查看结构化任务状态和日志。

### 这套机制的验收标准

- 新会话启动后，Claude 不依赖聊天历史就能说清当前唯一任务、下一步和验收标准。
- 任意时刻终止 Claude，下一会话能在 5 分钟内恢复长任务和项目状态。
- 用户提出临时新功能后，它会进入 backlog，不会自动打断主线。
- Claude 不能把部分完成误报为整个需求完成，需求矩阵能显示剩余差距。
- 没有可执行工作时，它会明确进入合法暂停状态；有同范围工作可做时不会无故结束。
- 后续 Codex 接手时读取同一套仓库文件即可继续，不需要依赖 Claude 私有 memory。

## 建议 Claude 接下来直接执行的顺序

1. 先核对云主机是否仍在计费、当前是否有正在进行的有效工作；若没有，立即提醒用户停机（不要释放）。
2. 修正 `cloud-full/STATUS.md` 的事实冲突，完成并运行 cloud preflight。
3. 为镜像缓存增加完整性/架构校验，确认当前传输是否可安全续跑。
4. 加集群 context/destructive guard，再继续任何 namespace、磁盘、PVC 级操作。
5. 用当前 cloud-full 环境完成 OPA 上线前差异盘点和真实权限闭环；切换必须让用户在场。
6. 完成环境 overlay/参数化，消除手工 `git mv` 和手调资源。
7. 为三个自建应用补测试、锁依赖、构建固定镜像；扩大 CI。
8. 最后再评估 ClickHouse、Notebook 开发体验等新增范围。

## 本轮不建议 Claude 做的事

- 不要为了显示进展继续新增组件或 ADR 数量。
- 不要在 cloud-full 部署过程中顺手重构无关模块。
- 不要把“有脚本”“写了配置”“本地 curl 成功”描述成生产能力完成。
- 不要以删除 namespace、强杀容器作为常规资源开关。
- 不要在没有 preflight 和立即可执行任务时让用户打开按量资源。
- 不要把公网 IP、个人本机私钥路径等易变实例信息继续扩散到更多长期文档；实例状态应集中管理，并在实例释放后及时清理。
