# 备份与恢复

每个操作统一成六段:**触发条件 / 影响 / 前置检查 / 操作 / 验证 / 回滚**。
"验证"那段是重点 —— 这里的每一条都吃过"命令成功但结果是错的"的亏。

## 现在备了什么、没备什么

| 数据 | 有备份? | 说明 |
|---|---|---|
| Postgres(Keycloak / Hive Metastore / MLflow / Airflow / Superset 共用) | ✅ 每天 02:00 UTC | `pg_dumpall` 全量 → MinIO `backups/postgres/`,留 14 天 |
| Keycloak realm / client / 用户 | ✅ | 就在上面那份里,不用单独处理 |
| MinIO 里的 Iceberg 表数据 | ❌ **刻意不备** | 理论上能从数据源重导,和 Postgres 里那些不可重建的元数据不是同一类风险([ADR-033](../decisions/033-postgres-backup.md))。**以后如果有不可重建的数据落进 MinIO,这个判断要重新做** |

## 恢复 Postgres(到一次性实例,用于演练或取数)

**触发条件**:想验证备份是不是真的能用;或者要从历史备份里捞某张表的
旧数据,但不想动线上库。

**影响**:无。全程不碰共用的活实例。

**前置检查**:

```bash
scripts/restore-postgres-backup.sh          # 不带参数 = 只列出可用备份
```

看得到备份列表,且**最新那份的大小不是几十字节**(见下面那条事故)。

**操作**:按脚本提示选一份备份,恢复进一次性 Postgres pod。

**验证** —— 三样都要,少一样都不算:

1. 预期的库都在(`\l` 能看到 keycloak / hive / mlflow / airflow / superset)。
2. **抽查一张真实业务表有内容**,比如 `keycloak.user_entity` 有行,不是空壳。
3. 行数量级和线上对得上。

**回滚**:删掉那个一次性 pod 就行。

## 恢复 Postgres(覆盖共用的活实例)

**触发条件**:线上数据真的坏了 / 丢了。

**影响**:**Keycloak、Hive Metastore、MLflow、Airflow、Superset 全部中断。**
Keycloak 一停,所有走 SSO 的组件跟着登不进去。**必须先和 zhenghe 约窗口。**

**前置检查**:

1. 先按上面那条做一次**一次性实例**的恢复演练,确认这份备份真的能用。
2. 确认当前故障真的需要整体恢复 —— 单库、单表的问题不要用全量覆盖解决。

**操作**:

```bash
scripts/restore-postgres-backup.sh <备份文件名>     # 会要求手动输入 yes
```

那个 `yes` 确认是**刻意的**:恢复是破坏性操作,不该由脚本替人决定。

**验证**:各组件能重新登录;抽查恢复前后都存在的一条真实数据。

**回滚**:**没有自动回滚。** 覆盖之前当天的备份就是唯一退路 —— 所以前置
检查里那条"先演练"不是形式。

> **这条路径整体还没有真的执行过一次。** 核心逻辑(下载 → port-forward →
> `gunzip | psql`)在 2026-08-13 的演练里间接验证过(手动跑的是同一套命令,
> 只是目标换成一次性 pod),但脚本作为整体、对着真实共用实例、包括它的
> 确认交互流程,没跑过。需要人明确安排一个能接受短暂中断的窗口。

## 2026-08-13 真实事故:20 字节的"成功"备份

`pg_dumpall | gzip > file` 这种写法**在管道里悄悄吞掉失败**,产出过一次
20 字节的空备份文件,而 Job 报告成功、退出码是 0。

**教训**:备份系统不能只信 Job/Pod 的退出码,要定期抽查产出物本身。上面
每条"前置检查"里那句"最新那份的大小不是几十字节",就是这次事故换来的。

详细过程和修复见 [ADR-033](../decisions/033-postgres-backup.md)。
